# 강화학습 제어(rlcontrol) 플러그인 사용 가이드 (v1.2.0)

## 개요

**강화학습(RL)을 장비/제어 시스템에 적용**하는 전문 워크플로 플러그인입니다.
① 적용 가능성 검토(게이트) → ② 알고리즘 검토·환경/보상/안전 설계 → ③ 구현(환경·에이전트·
학습 파이프라인) → ④ 성능·기능 테스트까지의 전체 흐름을 지원합니다.

이 플러그인의 페르소나는 **강화학습을 20년 이상 실제 장비 제어에 상용으로 적용해 온 전문가**로,
성능·안정성을 최적화하는 전략을 세우되 **무엇보다 RL이 정말 필요한지부터 냉정하게 판별**합니다.

> **가장 큰 차별점**: `rl-assess` 게이트는 **"RL 부적합 → 고전 제어 권장"(No-Go) 판정을 낼 수
> 있습니다.** 대부분의 제어 문제는 고전 제어(PID/LQR/MPC)로 충분하고, RL은 안전성·재현성·
> 샘플효율·검증난이도의 리스크를 들여옵니다. 이 플러그인은 RL을 팔지 않고, 필요한지부터
> 정직하게 판별합니다.

```bash

/plugin install rlcontrol@pjy-skills
```

셋업 시 프로젝트 경로를 질문합니다:

### 사전 준비 (선택)

RL 구현·학습을 실제로 돌리려면 Python 환경이 필요합니다. **강제는 아니며**, 검토·설계 단계는
코드 없이도 진행됩니다.

- Python 3.10+
- PyTorch
- Gymnasium (5-튜플 API)
- Stable-Baselines3 / CleanRL (온라인), d3rlpy (오프라인 RL)
- (선택) ONNX Runtime — 실시간 추론 배포

> 라이브러리 버전별 API 세부는 단정하지 말고 context7 MCP 또는 공식 문서로 확인합니다.

## 빠른 시작 — 검토→설계→구현→테스트→개선 파이프라인

### 1. 적용 가능성 검토 (게이트)

```
"우리 3축 스테이지 정밀 위치제어에 강화학습 적용할 수 있는지 검토해줘"
```

`rlctrl-feasibility-analyst`가 제어 대상·목표·관측 신호·액추에이터·안전 요구·시뮬레이터/로그
가용성·사이클타임을 인터뷰로 보충한 뒤, MDP 정식화 초안을 만들고 고전 제어(PID/LQR/MPC) 대비
타당성과 적용 가능성 체크리스트를 평가해 **Go/No-Go 판정 리포트**(문제 규격·MDP 초안·리스크
심각도·판정·권장 경로)를 산출합니다. **No면 고전 제어/하이브리드 권장안**을 제시합니다.

### 2. 알고리즘 검토·설계

```
"Go 판정 난 문제로 알고리즘 선정하고 보상/안전 설계해줘"
```

`rlctrl-algorithm-designer`가 행동공간(연속/이산)·샘플 예산·온라인/오프라인·안전 요구로부터
알고리즘을 선정하고(연속 첫 시도=SAC/PPO, 이산=PPO/DQN 계열, 실기 로그만=오프라인 RL, 안전
제약 강함=Safe RL), 환경 규격·보상 함수(reward hacking 방지·potential-based shaping)·안전
아키텍처(제약 MDP·Lagrangian·shielding·폴백)·하이퍼파라미터 시작점을 담은 설계 문서를 산출합니다.

### 3. 구현

```
"설계대로 Gymnasium 환경이랑 SAC 학습 파이프라인 구현해줘"
```

`rlctrl-implementer`가 `gymnasium.Env` 서브클래스(`reset -> (obs, info)`,
`step -> (obs, reward, terminated, truncated, info)` **5-튜플**)를 구현하고, 관측/행동 정규화·
벡터화·시뮬레이터 래퍼(안전 계층 삽입 지점)를 구성한 뒤, SB3/CleanRL 학습 파이프라인
(체크포인트·로깅·다중 시드 재현성)과 안전 계층·ONNX 실시간 추론 배포까지 작성합니다.
라이브러리 버전 세부는 context7/공식 문서로 확인합니다.

### 4. 성능·기능 테스트

```
"학습된 정책 다중 시드로 평가하고 안전·강건성 검증해줘"
```

`rlctrl-evaluator`가 **다중 시드(최소 5~10)·평균±신뢰구간·학습곡선**으로 성능을 평가하고
(베이스라인=고전 제어·랜덤·기존 정책 대비), 제약 위반율·정상상태 안정성·외란/파라미터 강건성·
워스트케이스·sim-to-real 검증을 수행해 PASS/FAIL·심각도·재현 조건을 붙인 리포트를 만듭니다.
**시뮬 성능이 곧 실기 성능이 아님**(sim-to-real 갭)을 명시하고 가드형 실기 전환 체크리스트를 제공합니다.

### 5. 지속 개선 (운영 후)

```
"운영하면서 쌓인 데이터로 모델 더 학습해서 성능 높여줘"
```

배포 후 쌓이는 운영 데이터는 RL의 가장 큰 자산입니다(데이터 플라이휠). 단, **실장비에서
온라인 학습하지 않고**, `rl-improve`가 수집→오프라인 재학습(CQL/IQL/TD3+BC)·offline-to-online
미세조정·시뮬레이터 재보정 중 경로를 선택 → champion/challenger 재검증 → **동일 실기 전환
가드 게이트 재통과** → 가드형 재배포(champion 보존·롤백 가능)의 관리된 루프로 진행합니다.

## "RL을 쓰면 안 되는 경우" 안내

`rl-assess` 게이트는 **No-Go 판정을 정직하게 냅니다.** 다음 신호가 있으면 고전 제어/하이브리드를
먼저 검토하세요.

- **고전 제어로 충분**: 선형·잘 모델링된 플랜트로 PID/LQR/MPC가 이미 요구 성능을 만족.
- **안전 크리티컬 + 시뮬레이터 없음 + 온라인 탐색 불가**: 안전한 학습 데이터를 확보할 방법이 없음.
- **재현성/검증이 최우선**: 인증·규제 대상이라 결정적·설명가능 제어기가 필요.
- **샘플 예산 부족**: 충실한 시뮬레이터도, 충분한 실기 로그도 없음.
- **보상 명세 곤란**: 목표를 보상으로 정직하게 표현하기 어렵고 reward hacking 위험이 큼.

이 경우 **하이브리드**(residual RL로 고전 제어기 위 잔차만 학습, RL로 MPC 비용/게인 튜닝)가
전면 RL보다 안전하고 실용적일 때가 많습니다.

## FAQ

**Q. 고전 제어(PID/LQR/MPC)와 강화학습, 어떻게 고르나요?**
A. 먼저 고전 제어로 풀 수 있는지 검토하는 것이 원칙입니다. 플랜트가 선형·잘 모델링되어 있고
요구 성능을 만족하면 고전 제어가 더 안전·재현성·검증성에서 유리합니다. RL은 고차원·강비선형·
모델 부정확·다목적 상충처럼 고전 제어가 한계를 보이는 문제에서 이득이 큽니다. `rl-assess`가
이 판단을 MDP 정식화·대비 분석·체크리스트로 근거와 함께 내려줍니다.

**Q. 시뮬레이터가 꼭 필요한가요?**
A. 온라인 RL은 방대한 상호작용을 요구하므로 **충실한 시뮬레이터가 사실상 전제**입니다. 실기에서
직접 탐색하면 안전·비용 문제가 큽니다. 시뮬레이터가 없고 실기 로그만 있으면 **오프라인
RL**(CQL/IQL 등)을 검토하고, 그마저 없으면 RL 적용이 어렵다는 신호입니다(게이트에서 판정).

**Q. 학습된 정책을 바로 장비에 올려도 되나요?**
A. 안 됩니다. **무제약·무보호 정책의 실기 직배포는 금지**입니다. 출력에 action clipping/shielding
안전 계층을 두고, 이상 시 인계할 **폴백 고전 제어기와 비상 정지**를 상시 대기시키며, **시뮬레이터
검증 → 사람 감독 하 가드형 실기 전환**(제한 속도·제한 영역) 순서를 지킵니다. 시뮬 성능은 곧
실기 성능이 아닙니다(sim-to-real 갭).

**Q. 학습은 Python인데 실기 구동은 C#/C++인데 어떻게 배포하나요?**
A. **학습·배포 언어를 분리**하는 것이 표준·권장 패턴입니다(Python 런타임을 실기에 얹지 않음).
학습이 끝나면 결정론적 정책망만 **ONNX**로 export하고, C#/C++ 구동 프로그램이 ONNX Runtime으로
추론합니다. 핵심 세 가지: (1) **정규화 패리티** — `VecNormalize`의 obs mean/var·clip과 행동
역스케일은 정책의 일부이므로 구동 프로그램에서 학습 때와 정확히 동일하게 재현해야 하고(불일치 시
조용히 오작동), (2) **안전 계층은 구동 프로그램 쪽** — action clipping·shielding·폴백 고전
제어기·비상 정지를 C#/C++에 구현합니다(Python SafetyWrapper는 학습용), (3) **패리티 테스트** —
같은 관측에 Python 추론과 C#/C++ 추론 결과가 허용 오차 내 일치하는지 검증합니다. 실시간에서는
세션 재사용·입출력 버퍼 사전 할당이 필수이고, C#은 GC 지터에 주의합니다(최저 지터가 필요하면
추론도 C++ 권장). 장비가 WMX3 기반이면 `wmx3app` 제어 루프에 연동합니다. 세부 절차는
`rl-implement`의 `references/cross-language-deployment.md`를, ONNX Runtime C++/C# API는 공식
문서·context7를 참조하세요.

**Q. 실기 데이터만 있고 온라인 탐색이 불가능하면요?**
A. **오프라인 RL**(CQL·IQL·TD3+BC·BCQ 등)을 검토합니다. 고정된 로그 데이터셋에서 정책을
학습하며, 데이터 분포 밖 행동의 과대평가를 억제하는 것이 핵심입니다. 다만 데이터 커버리지가
정책 품질의 상한을 정하므로, 로그가 목표 동작 영역을 얼마나 덮는지 먼저 평가합니다.

**Q. 장비에 적용한 뒤 쌓이는 운영 데이터로 추가 학습해 성능을 더 높일 수 있나요?**
A. 네 — 그것이 RL의 가장 큰 장점(데이터 플라이휠)이고 `rl-improve`가 담당합니다. 단 **실장비에서
배포 정책을 그대로 온라인 학습하는 것은 금지**합니다(탐색 위험·파국적 망각·검증 불가·자기 편향).
대신 관리된 루프로: ① 운영 로그를 전이 `(s, a, r, s')` 재구성 가능하게 수집 → ② 오프라인
재학습(CQL/IQL/TD3+BC) / 안전 계층 하 offline-to-online 미세조정 / 시뮬레이터 재보정 중 경로 선택
→ ③ 신규 정책(challenger)을 현 배포 정책(champion)과 다중 시드·회귀 스위트로 비교하고 **실기 전환
가드 게이트 10항목을 처음처럼 재통과** → ④ 사람 승인·(가능하면) shadow 평가 후 가드형 재배포,
champion은 보존해 즉시 롤백 가능하게 둡니다. 상세는 `rl-improve`의 `references/continual-learning.md` 참조.

**Q. 평가는 왜 다중 시드가 필수인가요?**
A. RL은 시드·초기화에 따라 성능 분산이 큽니다. 단일 시드 성능은 신뢰할 수 없어, **최소 5~10 시드
평균±신뢰구간**과 베이스라인 대비로 판정합니다("Deep RL That Matters", Henderson et al. 2018류
재현성·분산 함정). `rl-test`가 이 프로토콜을 강제합니다.

**Q. WMX3 모션 제어 장비와 연동되나요?**
A. 됩니다(선택). 장비가 WMX3 기반이면 `wmx3app`의 **SimuPlatform**을 학습·평가 환경(Gymnasium
래퍼)으로 감싸 쓰고, 실기 전환은 `wmx3-app-test`의 실기 전 체크리스트를 따를 수 있습니다.
강제 사항은 아니며, rlcontrol은 특정 하드웨어에 종속되지 않는 범용 제어 플러그인입니다.

**Q. 라이브러리 API가 문서와 다르면요?**
A. Gymnasium·Stable-Baselines3·CleanRL·d3rlpy 등은 버전에 따라 API가 달라질 수 있어, 세부
시그니처는 **단정하지 않고** context7 MCP(`mcp__plugin_context7_context7__*`) 또는 공식 문서로
확인합니다. 알고리즘 특성·수식은 확립된 사실(예: PPO=온폴리시, SAC=오프폴리시)만 기술합니다.
