# 강화학습 적용 가능성 검토 (게이트)

> 이 스킬은 제어 문제를 받아 **강화학습(RL)을 적용해야 하는가**를 판정하는 이 플러그인의 관문입니다.
> 실제 분석은 **rlctrl-feasibility-analyst 에이전트**에게 위임합니다 — **읽기 전용 분석**이며 코드/설계를 만들지 않습니다.
> `references/` 3개 문서(MDP 정식화·적용 가능성 체크리스트·RL vs 고전 제어)를 참조합니다.

## 핵심 원칙 — 정직한 게이트

강화학습을 20년 이상 실제 장비 제어에 **상용으로** 적용해 온 전문가의 관점에서, 이 스킬은 **RL을 파는 것이 아니라 RL이 필요한지 판별한다.** 실무에서 대부분의 제어 문제는 고전 제어(PID/LQR/MPC)로 충분하며, RL은 다음 리스크를 들여온다:

- **안전성** — 탐색(exploration) 중 위험한 행동, 실기에서의 무제약 정책
- **재현성·분산** — 시드에 따라 결과가 크게 달라짐, 성능 보장이 통계적
- **샘플 효율** — 수렴에 대량의 상호작용(수십만~수천만 스텝) 필요
- **검증 난이도** — Lyapunov 안정성 같은 형식 보장이 없는 블랙박스 정책

따라서 이 스킬은 **"RL 부적합 → 고전 제어 권장" 판정(No-Go)을 두려워하지 않으며**, 이것이 이 플러그인의 가장 큰 차별점이다. 안전 최우선: 장비 제어는 안전-크리티컬이므로 무제약 정책을 실기에 바로 배포하지 않고, 시뮬레이터 우선 검증 → 가드형 실기 전환을 전제한다.

## 입력

제어 문제 정보. 다음이 부족하면 **문제 정의 인터뷰**로 수집합니다.

### 문제 정의 인터뷰 체크리스트

| # | 항목 | 확인 내용 |
|---|------|----------|
| 1 | 제어 대상·목표 | 무엇을 제어하는가(축·프로세스·시스템), 성공 기준(정착시간·오버슈트·처리량·수율 등 정량 목표) |
| 2 | 현재 제어 방식 | 이미 쓰는 제어기(PID/LQR/MPC/게인스케줄/수동)와 그 한계 — **왜 지금으로 부족한가** |
| 3 | 관측 가능 신호 | 센서/피드백 목록, 노이즈·지연·결측, 상태가 관측으로 충분히 마르코프한가(POMDP 여부) |
| 4 | 액추에이터·행동 | 지령 종류(위치/속도/토크/이산 스위칭), 연속/이산, 물리 한계·레이트 제한 |
| 5 | 안전 요구 | 안전 한계(위치/속도/토크/온도), 위반 결과(장비 손상/인명), 비상 정지, 사람 감독 여부 |
| 6 | 시뮬레이터/데이터 | 고충실도 시뮬레이터 유무·검증 상태, 과거 로그 데이터 유무·양·품질(오프라인 RL 후보) |
| 7 | 실시간 제약 | 제어 주기(사이클타임), 추론 지연 예산, 온라인 탐색 허용 여부(실기에서 탐색 가능한가) |

## 검토 절차 (5단계)

1. **문제 정의 인터뷰** — 위 체크리스트로 문제를 표로 정리하고, 미확정 항목은 질문으로 확정한다. 특히 항목 2("왜 지금으로 부족한가")를 반드시 확인 — 현 제어기가 검증되지 않았거나 튜닝이 덜 된 상태면 RL이 아니라 **고전 제어 개선이 먼저**다.
2. **MDP 정식화** — 상태/행동/보상/전이/에피소드 경계·관측성을 정의한다. `references/mdp-formulation.md`의 정식화 가이드를 따른다. 잘못된 정식화가 RL 실패의 대부분 원인임을 유의(특히 마르코프성 결여·보상 오설계).
3. **고전 제어 대비 판정** — PID/LQR/MPC/게인 스케줄링/적응 제어로 충분한가를 먼저 판정한다. `references/rl-vs-classical.md`의 선택 기준을 따른다. **"고전 제어로 되는 문제면 RL을 쓰지 않는다"**가 기본값.
4. **적용 가능성 체크리스트** — 안전 크리티컬성·샘플 예산·시뮬레이터 충실도·sim-to-real 갭·데이터 가용성·보상 명세 난이도·실시간 추론·검증 가능성을 항목별로 평가한다. `references/feasibility-checklist.md`의 15~20항목 체크리스트와 Go/No-Go 결정 규칙을 적용한다. 각 리스크에 심각도(CRITICAL/MAJOR/MINOR/INFO)를 부여한다.
5. **Go/No-Go 판정 + 근거 리포트** — 아래 산출물 형식으로 판정을 낸다. **No-Go면 고전 제어/하이브리드 권장안**, **Go면 다음 단계(rl-design)로 넘길 문제 규격서**를 함께 제시한다. 애매하면 "조건부 Go"(예: 시뮬레이터 확보 후 진행)로 명확히 구분한다.

## 산출물: 적용 가능성 판정 리포트

```markdown
# {대상} 강화학습 적용 가능성 판정 리포트

## 1. 문제 규격          ← 인터뷰 결과 표(대상·목표·현 제어·관측·행동·안전·데이터·실시간)
## 2. MDP 초안           ← 상태공간 / 행동공간 / 보상 초안 / 전이 성질 / 에피소드 경계 / 할인율 / 관측성(MDP vs POMDP)
## 3. 고전 제어 대비      ← PID/LQR/MPC로의 충족 가능성 판정과 근거
## 4. 리스크 목록         ← 항목별 심각도(CRITICAL/MAJOR/MINOR/INFO)와 완화책
## 5. 판정               ← **Go / 조건부 Go / No-Go** + 한 문단 근거
## 6. 권장 경로          ← No-Go: 고전/하이브리드 권장안 / Go: rl-design으로 넘길 문제 규격서
```

리스크 심각도는 레포 관례에 따라 **CRITICAL / MAJOR / MINOR / INFO** 4등급으로 표기합니다.

### 판정 요약 예시

```
== 강화학습 적용 가능성 판정 ==

대상: 단일 서보축 위치 정착 제어 (현재 PID, 정착시간 개선 요구)
판정: 🔴 No-Go

근거: 대상 동역학이 근사 선형·고충실도 모델 확보 가능이며, 요구가 단일 목표
      정착시간 단축이다. LQR/MPC로 제약을 명시적으로 다루며 최적 성능에 도달
      가능하고, 현재 PID는 튜닝 여지가 남아 있다. RL이 들여올 안전·재현성·
      검증 리스크 대비 이득이 불명확하다.

권장 경로: ① PID 게인 재튜닝(또는 자동튜닝) → ② 부족 시 제약 처리가 필요하면 MPC 전환
          → ③ 그래도 비선형·다목적 요구가 드러나면 그때 RL 재검토(하이브리드 우선)

리스크:
  🔴 CRITICAL  안전 한계 위반 시 장비 손상 — 무제약 정책 실기 탐색 불가
  🟠 MAJOR     고충실도 시뮬레이터 미검증 — sim-to-real 갭 리스크
  🟡 MINOR     현 PID 튜닝 미완 — RL 이전에 고전 제어 개선 여지
```

## rlctrl-feasibility-analyst 에이전트 위임

이 스킬은 실제 검토 작업을 `rlctrl-feasibility-analyst` 에이전트에게 위임합니다. **에이전트는 읽기 전용으로 동작하며 코드/설계를 만들지 않습니다** — Go 판정이 나면 설계는 `rl-design` 스킬(rlctrl-algorithm-designer 에이전트)로 진행합니다.

에이전트에게 전달할 정보:
- 수집된 문제 규격(인터뷰 결과 표)과 성공 기준(정량 목표)
- 현재 제어 방식과 그 한계(있으면 관련 코드/설정 경로)
- 안전 요구·안전 한계, 온라인 탐색 허용 여부
- 시뮬레이터/로그 데이터 가용성과 검증 상태
- 실시간 제약(사이클타임·추론 지연 예산)
- **references 정본 절대 경로: `${CLAUDE_SKILL_DIR}/references/` 아래 문서들 — 호출 시 실제 절대 경로로 치환하여 전달** (에이전트는 `.claude/agents/`로 단독 설치되어 상대 references 경로가 깨지므로, `mdp-formulation.md`·`feasibility-checklist.md`·`rl-vs-classical.md`의 절대 경로를 명시적으로 전달)
