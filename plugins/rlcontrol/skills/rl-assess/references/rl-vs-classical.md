# RL vs 고전 제어 — 정직한 선택 기준

> **용도**: rl-assess의 3단계에서 "고전 제어로 충분한가"를 먼저 판정한다.
> **입장**: 이 문서는 RL을 옹호하지 않는다. 실무 전문가는 **RL이 답이 아닌 경우가 훨씬 많다**는 것을 알고,
> RL을 쓰기 전에 고전 제어를 배제할 근거를 요구한다. "RL이 안 되는 이유"가 아니라 "고전 제어가 안 되는 이유"를 증명해야 RL로 간다.

## 1. 고전 제어기 요약 (무엇을 언제)

| 제어기 | 필요 조건 | 강점 | 한계 |
|--------|-----------|------|------|
| **PID** | 모델 거의 불필요, 단일 루프 | 보편적·튜닝 직관적·검증 용이·저연산 | 제약 미처리, 강한 비선형·다변수 커플링에 약함, 큰 지연에 취약 |
| **LQR** | 선형 모델(A,B)·2차 비용 | 상태피드백 최적해 K, 안정성·명료성 | 제약 미처리, 선형·정확 모델 전제, 상태 관측 필요 |
| **MPC** | 모델 + 온라인 최적화 | **제약을 명시적으로 처리**, 예측 시야, 다변수 | 온라인 연산 큼, 모델 정확도에 민감, 튜닝(비용/시야) 필요 |
| **게인 스케줄링** | 작동점별 선형화 모델 | 넓은 작동 범위에서 선형 제어 확장 | 스케줄 설계 수작업, 작동점 사이 보장 약함 |
| **적응 제어(MRAC/자기튜닝)** | 파라미터 불확실성 구조 有 | 파라미터 변동에 온라인 적응 | 설계 복잡, 안정성 증명 조건 까다로움 |

**요지**: 선형·저차원이면 LQR, 제약이 핵심이면 MPC, 단순 루프면 PID로 대개 충분하다.
이 셋으로 사양을 충족할 수 있으면 **RL을 쓰지 않는다** — 안정성 보장·해석성·저연산·검증 용이성이라는 결정적 이점을 포기할 이유가 없다.

## 2. RL과 고전 제어의 근본 차이

| 관점 | 고전 제어(PID/LQR/MPC) | 강화학습(RL) |
|------|------------------------|--------------|
| 모델 | 모델 기반(LQR/MPC) 또는 무모델 튜닝(PID) | 모델 프리로 데이터에서 정책 학습(모델기반 RL은 예외) |
| 최적성 | 가정 하 최적(LQR)·수치 최적(MPC) | 보상 극대화 근사 최적(수렴·분산 이슈) |
| 안정성 보장 | Lyapunov·이득/위상 여유 등 **형식 보장** | 일반적으로 형식 보장 없음(Safe RL도 제한적) |
| 제약 처리 | MPC는 명시적 처리 | 보상/제약 MDP/shielding으로 간접·근사 |
| 해석성 | 높음(게인·극 배치) | 낮음(블랙박스 신경망) |
| 연산 | 온라인 최적화(MPC)~저연산(PID) | 학습은 무겁고 추론은 가벼움(소형망 μs) |
| 개발 비용 | 모델링·튜닝 | 환경/보상/안전 설계 + 대량 샘플 + 튜닝 + 검증 |
| 강점 영역 | 선형·모델 가용·인증 필요 | 비선형·고차원·다목적·모델링 난해 |

## 3. "RL이 답이 아닐 때" — No-Go 신호 (정직하게)

다음 중 하나라도 강하게 해당하면 RL을 보류/배제하고 고전 제어를 권한다:

- **선형·저차원 + 정확한 모델** → LQR/MPC가 더 낫다. RL은 얻을 게 없고 리스크만 는다.
- **현 제어기가 튜닝·검증 미완** → 먼저 그것을 개선하라. "PID가 안 된다"의 상당수는 튜닝 문제다.
- **안전 크리티컬 + 시뮬레이터 없음 + 온라인 탐색 불가** → 안전하게 학습할 경로 자체가 없다.
- **형식 인증·안정성 증명 필수(항공·의료·기능안전)** → 블랙박스 정책의 인증 부담이 과도하다.
- **보상을 편법 없이 명세 불가** → 목표를 인코딩 못하면 RL은 엉뚱한 것을 최적화한다.
- **데이터·샘플 예산 부족** → 수렴에 필요한 상호작용을 확보 못하면 학습이 성립하지 않는다.
- **성능 이득이 불명확(ROI 낮음)** → 고전 제어 대비 개선 폭이 리스크·비용을 정당화하지 못한다.

> 이 신호들은 `feasibility-checklist.md`의 Go/No-Go 규칙과 직접 연결된다. rl-assess는 이를 근거로 **No-Go 판정을 당당히 낸다.**

## 4. "RL을 고려할 만할 때" — Go 신호

- 비선형·고차원·접촉풍부·하이브리드 동역학으로 **모델링/MPC가 어렵다**.
- 상충하는 다목적 절충이나 **환경 변화 적응**이 본질이고 수작업 튜닝이 한계에 왔다.
- **고충실도 시뮬레이터**가 있거나 값싼 대량 상호작용이 가능하다.
- 풍부한 **운전 로그**가 있어 오프라인 RL로 안전하게 정책을 얻을 수 있다.
- 고전 제어가 **성능 천장**에 도달했고, 안전 계층·폴백을 구성할 수 있다.

이 경우에도 무제약 정책을 실기에 직배포하지 않는다 — 시뮬레이터 우선 검증 → 가드형 실기 전환이 전제다.

## 5. 하이브리드 — RL과 고전 제어를 함께 (실무 최선인 경우가 많다)

순수 RL(end-to-end 토크 제어)보다 **하이브리드**가 안전·검증·샘플효율에서 유리한 경우가 많다.
"RL이냐 고전이냐"의 이분법 대신 다음 패턴을 우선 검토한다:

- **Residual RL(잔차 학습)**: `u = u_classical + u_RL`. 검증된 고전 제어기를 기반으로 두고 RL은 **잔차(보정항)**만 학습.
  탐색 범위가 작아 안전하고 샘플효율이 좋으며, RL이 실패해도 기반 제어기가 안전을 보장한다.
- **RL이 상위 파라미터를 조정**: RL이 직접 토크를 내지 않고 **MPC의 비용 가중치·시야**나 **PID 게인**,
  **세트포인트/궤적**을 조정한다(게인 스케줄링의 학습판). 하위 제어기가 안정성·제약을 담당.
- **RL로 초기값·워밍스타트**: MPC의 웜스타트나 비선형 최적화 초기해를 RL로 제공해 온라인 연산을 줄인다.
- **모델기반 RL + MPC**: 학습된 동역학 모델 위에서 MPC로 계획(MBRL). 해석성·제약 처리를 일부 회복.
- **안전 계층(shielding)으로 감싼 RL**: RL 정책의 출력을 안전 필터(제어 불변집합·CBF·규칙 기반)가 검사·수정.

**권고**: Go 판정이더라도 순수 RL보다 하이브리드를 먼저 제안하라. 대부분의 산업 적용에서 하이브리드가
"고전 제어의 안전·검증 + RL의 적응·성능"을 절충하는 현실적 해답이다. 설계 상세는 rl-design의
`reward-and-safety.md`(안전 계층)와 `algorithm-selection.md`(오프라인/Safe RL 선택)로 이어진다.

## 6. 판정 요약 템플릿 (rl-assess 리포트 §3에 반영)

```
고전 제어 대비 판정:
  - PID로 충족 가능?   [예/아니오 + 근거]
  - LQR로 충족 가능?   [예/아니오 + 근거(선형·모델 가용성)]
  - MPC로 충족 가능?   [예/아니오 + 근거(제약·연산 예산)]
  - 결론: [고전 제어로 충분 → No-Go] /
          [고전 제어 한계 확인 → 하이브리드 우선 검토] /
          [순수 RL 필요 근거 확립 → Go]
```

## 7. 도메인별 1차 권장 (참고 매핑)

특정 하드웨어에 종속되지 않는 일반 지침이다. 실제 판정은 언제나 체크리스트로 확정한다.

| 전형적 제어 문제 | 1차 권장 | RL 고려 조건 |
|------------------|----------|--------------|
| 단일축 위치·속도 정착 | PID / LQR | 강한 비선형·마찰·다목적이 드러날 때만 residual RL |
| 온도·유량 프로세스 제어 | PID / MPC(제약) | 강결합 다변수·큰 지연으로 MPC 튜닝이 한계일 때 |
| 다변수·제약 있는 궤적 최적 | MPC | 모델링 난해·온라인 연산 과다 시 MBRL/RL 파라미터 조정 |
| 접촉풍부 조립·그래스핑 | 힘제어 + (residual) RL | 시뮬레이터/데이터 확보 시 RL 유리(비선형 접촉) |
| 넓은 작동범위 비선형 | 게인 스케줄링 / MPC | 스케줄 수작업 한계 시 RL로 스케줄 학습 |
| 파라미터 시변(마모·부하) | 적응 제어 | 구조 미상·다목적이면 RL(비정상성 대응 전제) |
| 로그만 있고 탐색 불가 | 시스템 식별 + MPC | 로그 풍부하면 오프라인 RL(CQL/IQL) + OPE |

> 표의 왼쪽(1차 권장)이 사양을 충족하면 거기서 멈춘다. RL 열은 "왼쪽이 증명된 한계에 도달했을 때"만 발동한다.

## 8. 흔한 오해 바로잡기 (정직성)

- **"RL은 모델이 필요 없으니 편하다"** — 무모델은 맞지만 그 대가로 대량 샘플·환경·보상·안전 설계가 필요하다. 총비용은 대개 더 크다.
- **"딥러닝이니 더 좋은 성능"** — 선형·모델 가용 문제에서 RL이 LQR/MPC를 이기는 경우는 드물다. 오히려 분산·불안정으로 진다.
- **"시뮬레이터에서 잘 되면 실기도 된다"** — sim-to-real 갭 때문에 거짓이다. 시뮬 성능은 필요조건일 뿐 충분조건이 아니다.
- **"한 번 학습하면 끝"** — 마모·드리프트로 정책은 열화된다. 모니터링·재학습 없이는 운영이 성립하지 않는다.
- **"안전은 보상에 페널티로 넣으면 된다"** — 페널티는 위반을 줄일 뿐 보장하지 않는다. 안전은 shielding·제약·폴백으로 분리해야 한다.

> **크로스 플러그인**: 대상이 WMX3 모션 제어 기반이면 하이브리드의 하위 고전 제어기·폴백을 WMX3 API로 구성하고,
> 학습 환경은 `wmx3app`의 SimuPlatform(Gymnasium 래퍼)을 쓸 수 있다(강제 아님, 참고).
