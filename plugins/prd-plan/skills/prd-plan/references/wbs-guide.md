# WBS 작성 가이드 — 작업 분해와 의존 관계

## TASK 블록 규격 (기계 파싱 대상)

```markdown
### TASK-012 — 축 상태 조회 API 구현

- **근거 요구사항**: REQ-020, REQ-021
- **선행**: TASK-005, TASK-008        <!-- 없으면 "없음" -->
- **규모**: M                          <!-- S | M | L | XL -->
- **산출물**: `src/api/axes.cpp`, OpenAPI 스키마 갱신
- **완료 기준**: AC-020-1, AC-020-2 통과 + 계약 스키마 검증 테스트 green
- **차단 요인**: (선택) OPEN-003 결정 필요
```

규칙:
- ID는 `TASK-` + 3자리 연번. 재사용·재배치 금지
- **근거 요구사항은 필수.** 없으면 그 작업은 범위 밖이거나 PRD 누락 → 둘 중 무엇인지 밝힌다
- **완료 기준은 PRD의 AC를 참조**한다. 새 판정 기준을 여기서 만들지 않는다 (만들어야 한다면 PRD가 부실한 것)
- 산출물은 파일·문서·측정 결과 등 **존재를 확인할 수 있는 것**으로 쓴다

## 분해 원칙

| 원칙 | 내용 |
|------|------|
| **완료 판정 가능** | 끝났는지 애매한 작업은 분해가 잘못된 것 |
| **한 사람이 한 흐름으로** | 여러 역할이 동시에 붙어야 끝나는 단위는 쪼갠다 |
| **XL 금지** | XL이 남아 있으면 분해 미완. 반드시 L 이하로 쪼갠다 |
| **7±2** | 한 그룹의 하위 작업이 9개를 넘으면 중간 그룹을 만든다 |
| **검증을 별도 TASK로** | 구현과 검증을 한 TASK에 넣으면 자기검증이 된다 (레포 원칙: 작성/검증 분리) |
| **문서·배포도 작업이다** | 매뉴얼, 마이그레이션, 롤백 절차를 빼먹지 않는다 |

## 규모 등급 (시간이 아니라 상대 크기)

| 등급 | 기준 |
|------|------|
| **S** | 단일 파일·단일 함수 수준, 불확실성 없음 |
| **M** | 여러 파일에 걸치지만 방식이 명확함 |
| **L** | 설계 판단이 필요하거나 외부 의존이 있음 |
| **XL** | 불확실성이 커서 크기를 못 매기는 상태 → **분해 대상** |

`estimation-policy.md`를 반드시 함께 지킨다 (시간·날짜·인원 금지).

## 의존 관계

### 표기

```markdown
## 3. 의존 그래프

| TASK | 선행 | 병행 가능 | 비고 |
|------|------|-----------|------|
| TASK-001 | 없음 | — | 착수 가능 |
| TASK-005 | TASK-001 | TASK-006 | |
| TASK-012 | TASK-005, TASK-008 | — | OPEN-003에 차단됨 |
```

선택적으로 mermaid를 덧붙인다(렌더 환경에서 유용):

````markdown
```mermaid
graph LR
  T001[TASK-001 환경 구축] --> T005[TASK-005 계약 확정]
  T005 --> T012[TASK-012 API 구현]
```
````

### 규칙

- **순환 금지.** 순환은 분해 실패 신호 — 공통 선행을 뽑아내 끊는다
- **미정의 선행 금지.** 존재하지 않는 TASK를 선행으로 쓰지 않는다
- **미결 이슈 의존을 숨기지 않는다.** OPEN-###에 막힌 작업은 `차단 요인`에 명시하고 마일스톤 판정에 반영한다
- 병행 가능 작업을 표시하면 이후 `parallel-delegation`으로 동시 실행하기 쉽다

## 마일스톤

날짜가 아니라 **완료 조건의 묶음**으로 정의한다.

```markdown
## 4. 마일스톤

### M1 — 계약 확정
- 포함: TASK-001, TASK-005
- 완료 조건: API 스키마가 프론트/백엔드 양측에서 합의되고 검증 테스트가 존재
- 이후 가능해지는 것: 프론트·백엔드 병행 착수

### M2 — 기능 완성
...
```

기본 마일스톤 구성 제안:
- software: M1 계약/골격 → M2 기능 완성 → M3 검증·배포
- hardware-firmware: M1 사양 확정 → M2 회로/아트웍 → M3 시제품 브링업 → M4 검증
- research-PoC: M1 환경·베이스라인 → M2 실험 → M3 판정(중단 기준 포함)

## 요구사항 커버리지 매트릭스 (7절)

```markdown
| REQ | 강도 | 커버 TASK | 상태 |
|-----|------|-----------|------|
| REQ-001 | MUST | TASK-003, TASK-011 | 커버됨 |
| REQ-007 | SHOULD | — | **미커버** (사유: 2차 범위로 합의) |
```

- **MUST REQ 미커버는 CRITICAL이다.** 사유 없이 비어 있으면 계획이 불완전하다
- SHOULD/MAY 미커버는 사유를 적으면 허용

## 실행 리스크 (5절)

PRD 리스크를 승계하고, **계획 단계에서만 보이는 리스크**를 추가한다.

- 최장 의존 사슬(직렬 구간)이 길다 → 한 곳이 밀리면 전체가 밀린다
- 단일 작업에 지식이 집중됨
- 외부 납기·부품 리드타임에 걸린 작업
- 미결 이슈가 초기 마일스톤을 막고 있음
