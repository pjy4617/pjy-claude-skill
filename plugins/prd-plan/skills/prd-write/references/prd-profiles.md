# PRD 프로파일 — 코어 + 3종(software는 스택 변형 3종)

`prd-template-core.md`의 12섹션은 공통이고, 프로파일은 **7절(요구사항)과 8절(제약)에 필수 항목을 추가**한다.

## 선택 기준

| 프로파일 | `stack` | 고르는 경우 | 대표 다운스트림 |
|----------|---------|-------------|-----------------|
| `software` | `frontend` | React 화면·대시보드·조작 UI | react-vite |
| `software` | `backend` | C++ / C# / Python 서버·서비스·엔진·CLI | 일반 구현, wmx3app(응용), rlcontrol(배포측) |
| `software` | `full-stack` | 위 둘을 한 프로젝트로 | react-vite + 백엔드 |
| `hardware-firmware` | — | 보드·MCU 펌웨어·FPGA·모션 장비·계측 | kicad-design, stm32f4, vivado, wmx3app |
| `research-PoC` | — | 가설 검증·타당성 조사·알고리즘 실험 | rlcontrol(rl-assess) |

프론트매터에는 두 필드를 모두 적는다.

```yaml
profile: software
stack: full-stack        # software일 때만. 다른 프로파일은 생략
```

경계 사례:
- 장비 제어 SW(C++/C#) + 조작 화면(React) → `software` / `full-stack`. 장비 자체를 만드는 것이 아니면 hardware-firmware가 아니다
- 보드 + 그 위의 펌웨어 → `hardware-firmware` 하나로 쓰고 요구사항을 HW/FW 그룹으로 나눈다
- 펌웨어(보드) + PC측 응용(C#) → 주 산출물 기준으로 고르고, 나머지는 **연동 요구** 그룹으로 넣는다
- 애매하면 **요구 항목이 더 많은 쪽**을 고른다

## A. `software`

### A-공통 (스택 무관 필수)

**요구사항 그룹**
1. 기능 요구 — 사용자가 무엇을 할 수 있는가
2. 데이터 요구 — 저장·보존·마이그레이션·개인정보
3. 비기능 요구 — 성능(수치), 가용성, 보안, 로깅/관측
4. 연동 요구 — 외부 API·인증·기존 시스템

**제약 필수 항목**: 대상 환경/런타임 버전 / 배포 방식 / 기존 시스템 호환 / 규정

---

### A-1. `stack: frontend` (React)

> `react-vite` 플러그인이 소비한다. 아래 항목이 비면 구현 단계에서 되묻게 된다.

**추가 필수 항목**

| 항목 | 내용 | 미정일 때 |
|------|------|-----------|
| **화면 목록** | 화면/뷰 단위로 나열 + 각 화면의 핵심 사용자 작업 | 최소 화면 이름만이라도 |
| **UI 라이브러리** | Fluent UI v9 / shadcn(Radix+Tailwind) 중 **프로젝트당 택1** (react-vite 규약) | `(미정 — OPEN-###)` |
| **상태·데이터 흐름** | 서버 상태 갱신 주기, 실시간 여부(폴링/WebSocket/SSE), 낙관적 갱신 필요성 | 실시간 여부만이라도 확정 |
| **백엔드 계약** | 호출할 API 목록 또는 "백엔드 REQ-### 참조". full-stack이면 A-3의 인터페이스 계약으로 |
| **대상 브라우저·해상도** | 최소 지원 브라우저, 데스크톱/태블릿/모바일, 최소 해상도 | 사내 전용이면 그 사실을 명시 |
| **접근성 요구** | 키보드 조작 필수 여부, 스크린리더, 대비. 현장 장비 UI면 **장갑 조작·터치 타겟 크기** | 없으면 "요구 없음" 명시 |

**성능 AC 예시(관측 가능해야 함)**: 초기 렌더 1.5s 이하(로컬망), 실시간 차트 60fps 유지(1000점 갱신), 리스트 10k행 스크롤 시 프레임 드롭 없음

**비범위 단골**: 다국어, 다크모드, 모바일 대응, 오프라인 동작, 사용자 권한 관리 — **필요 없으면 명시적으로 비범위에 적는다**

### A-2. `stack: backend` (C++ / C# / Python)

**추가 필수 항목**

| 항목 | 내용 |
|------|------|
| **언어·런타임** | C++(표준 버전·컴파일러·빌드시스템) / C#(.NET 버전·프레임워크) / Python(버전·패키지 매니저). 혼용이면 컴포넌트별로 |
| **실행 형태** | 상주 서비스 / CLI / 라이브러리(DLL·so·패키지) / 실시간 태스크. Windows 서비스·systemd·컨테이너 여부 |
| **인터페이스 계약** | 제공하는 API(REST/gRPC/IPC/공유메모리/파일)와 소비하는 외부 API. 버전 정책 |
| **동시성·성능** | 예상 부하, 동시 처리 수, 처리 지연 목표(p95), 스레드 모델. **제어·계측이면 주기와 지터 상한** |
| **자원 제약** | 메모리 상한, 실시간성 요구(GC 허용 여부 — C#/Python은 여기서 걸린다), 시작 시간 |
| **오류·복구** | 장애 시 동작(재시작/페일세이프/안전 정지), 로그 레벨·보존, 관측 지표 |
| **데이터·영속성** | DB/파일 포맷, 스키마 변경 정책, 백업·보존 기간 |

**언어별로 특히 빠뜨리는 것**
- **C++**: 대상 OS/툴체인, 서드파티 라이선스, 정적/동적 링크, 실시간(RT) 요구 시 금지 사항(동적 할당·블로킹 호출)
- **C#**: .NET 버전과 배포 형태(self-contained 여부), GC 일시정지 허용치, `IDisposable` 수명 규약이 필요한 네이티브 자원
- **Python**: 버전 고정과 배포 방식(venv/컨테이너/PyInstaller), GIL이 성능 요구와 충돌하는지, 네이티브 확장 의존

**성능 AC 예시**: 1000 req/s에서 p95 40ms 이하, 제어 주기 1ms 지터 ±50µs 이내, 24시간 연속 운전 메모리 증가 5% 이하

### A-3. `stack: full-stack`

A-1 + A-2 필수 항목을 모두 포함하고, **추가로 접점 하나를 반드시 문서화한다**.

**인터페이스 계약 섹션(필수)** — 프론트/백엔드 분업의 90%의 분쟁이 여기서 난다.

```markdown
### REQ-020 — 축 상태 조회 API

- **강도**: MUST
- **엔드포인트**: GET /api/axes/{id}/status
- **요청**: id (int, 0~127)
- **응답**: { position: number(mm), state: "idle"|"moving"|"error", errorCode: int }
- **갱신 주기**: 프론트 폴링 100ms (실시간 스트림은 비범위)
- **오류**: 404 미존재 축 / 503 통신 두절 시 마지막 값 + stale=true
- **수용 기준**:
  - AC-020-1: 계약 위반 응답이 없다 (스키마 검증 테스트 통과)
  - AC-020-2: 통신 두절 상태에서 프론트가 stale 표시를 노출한다
```

계약이 아직 없으면 **"API 계약은 OPEN-###에서 확정"**으로 남기고, 프론트/백엔드 요구사항이 그 미결에 의존한다고 명시한다.

## B. `hardware-firmware`

> 이 프로파일의 PRD는 같은 마켓플레이스의 `kicad-design`(회로도 생성)·`stm32f4`·`vivado`가 **입력으로 직접 소비**한다.
> `kicad-design`이 요구하는 4항목(기능 요구사항 / 인터페이스 목록 / 성능 사양 / 전원 요구)을 반드시 채운다.

**요구사항 그룹 (필수 4 + 선택)**

1. **기능 요구** — 보드/장치가 수행할 동작. REQ 블록 규격 그대로
2. **인터페이스 목록** — 표로 작성

   | ID | 인터페이스 | 규격 | 방향 | 전압/레벨 | 커넥터 | 비고 |
   |----|-----------|------|------|-----------|--------|------|
   | REQ-010 | EtherCAT | 100BASE-TX ×2 | I/O | 3.3V LVCMOS + 자기결합 | RJ45 | 데이지체인 |

3. **성능 사양** — 측정 가능한 수치만 (샘플링 레이트, 지연, 분해능, 정밀도, 제어 주기)
4. **전원 요구** — 표로 작성

   | 레일 | 전압 | 최대 전류 | 정밀도 | 시퀀스 | 소스 |
   |------|------|-----------|--------|--------|------|
   | +3V3 | 3.3V | 1.2A | ±3% | VDD 후 10ms | DC-DC |

5. (선택) 기구/폼팩터 — 치수, 마운팅홀, 높이 제한, 커넥터 위치
6. (선택) 환경·규격 — 동작 온도, EMC/안전, IP 등급, 진동
7. (선택) 펌웨어 요구 — 부팅 시간, 업데이트 방식, 안전 상태, 워치독, 실시간성

**제약 필수 항목**: MCU/FPGA 지정 또는 후보 / 공급 가능성(단종·리드타임) / 층수·기판 제약 / 인증 요구 / 기존 하네스·기구 호환

**미확정이 많은 것이 정상이다.** 부품 선정 전이면 `(미정 — OPEN-###)`로 남기고 요구 수치만 확정한다.

## C. `research-PoC`

**요구사항 그룹**
1. **검증할 가설** — 반증 가능한 형태로 (`X 조건에서 Y가 Z 이상이다`)
2. **판정 기준** — 성공/실패를 가르는 수치와 베이스라인. **이것이 없으면 PoC가 끝나지 않는다**
3. 실험 요구 — 데이터·환경·측정 방법·반복 횟수
4. 산출물 요구 — 리포트·재현 스크립트·모델 아티팩트

**제약 필수 항목**: 가용 데이터/시뮬레이터 / 계산 자원 / 기간 상한(사용자 제공 값만) / 실기 적용 금지 범위(안전)

**필수 섹션 추가**: `중단 기준(Stop Criteria)` — 어떤 결과가 나오면 **그만두는가**.

## 프로파일 공통 주의

- 프로파일·스택을 바꾸면 필수 섹션이 달라진다 → 프론트매터를 갱신하고 누락 섹션을 채운다
- 다운스트림 스킬이 정해져 있으면 참고 자료 섹션에 명시한다 (예: `다음 단계: react-vite / kicad-design`)
- 프로파일 필수 항목이 인터뷰에서 확정되지 않았다면 **빈 섹션을 만들지 말고** 미결 이슈로 등록한 뒤 `(미정 — OPEN-###)`만 남긴다
