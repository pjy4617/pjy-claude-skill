# 검수 루브릭 — 7카테고리 · 4등급

`prd-reviewer` 에이전트와 `prd-review` 스킬의 공통 정본. PRD·PLAN·체크리스트 모두에 적용하되, 카테고리별 점검 항목은 문서 종류에 따라 달라진다.

## 등급 정의 (고정)

| 등급 | 정의 | 승격 조건 |
|------|------|-----------|
| **CRITICAL** | 이 문서로 착수하면 **재작업이 확실** | "무엇이 어떻게 다시 만들어져야 하는가"를 한 문장으로 쓸 수 있어야 함 |
| **MAJOR** | 개발 중 **분쟁·지연이 높은 확률로** 발생 | 분쟁 당사자와 쟁점을 지목할 수 있어야 함 |
| **MINOR** | 품질 저하이나 진행 가능 | — |
| **INFO** | 참고 의견 | — |

**등급 인플레 금지**: 승격 조건 문장을 못 쓰면 한 단계 내린다. CRITICAL 남발은 검수 신뢰도를 깎고 3라운드 안에 수렴하지 못하게 만든다.

## 검수 경계 (지적 대상 / 비대상)

| 지적한다 | 지적하지 않는다 |
|----------|-----------------|
| 두 가지로 해석되는 요구 | 문체·표현 취향, 섹션 순서 |
| AC 부재·측정 불가 | 구현 기술 선택(→ 필요시 INFO만) |
| 범위 경계 부재 | 다음 단계에서 정하면 되는 세부 |
| 문서 내부 모순·추적성 단절 | 현 단계에서 결정 불가한 사항(→ **미결 이슈 등록 권고**로 적는다) |
| 실행 불가 계획(순환·미정의 선행) | 작성자의 판단이 자신과 다른 것 자체 |
| 치명 리스크·가정 누락 | 이미 미결 이슈로 등록된 미정 값 |

## 카테고리별 점검 항목

### 1. 완결성

- [ ] 프로파일(+stack) 필수 섹션이 모두 존재하는가 (`prd-profiles.md` 대조)
- [ ] 빈 섹션·플레이스홀더(`TBD`, `TODO`, `{{...}}`, `...`)가 남아 있지 않은가 → **남아 있으면 CRITICAL**
- [ ] 비범위 3항목 이상인가 → 미달이면 MAJOR
- [ ] 리스크 3건 이상, 각각 완화책이 있는가
- [ ] 미결 이슈 표가 있는가 (없으면 "없음" 명시 필요)

### 2. 명확성

- [ ] 금지어(`등등`,`기타`,`적절히`,`필요시`,`가능한 한`,`사용자 친화적`,`빠르게`,`안정적으로`)가 요구사항·AC에 남았는가 → 남으면 MAJOR
- [ ] 한 REQ에 요구가 두 개 이상 섞이지 않았는가
- [ ] 강도(MUST/SHOULD/MAY)가 명시되었는가
- [ ] 용어가 문서 전체에서 일관되게 쓰이는가 (같은 대상을 두 이름으로 부르지 않는가)

```bash
grep -nE "등등|기타|적절히|필요시|가능한 한|최대한|사용자 친화적|직관적|빠르게|안정적으로|효율적으로|충분히" <문서>
grep -nE "TBD|TODO|\{\{|FIXME|추후 결정" <문서>
```

### 3. 측정가능성

- [ ] 모든 REQ에 AC가 있는가 → 없으면 MAJOR (여러 건이면 CRITICAL)
- [ ] AC가 **관측 가능**한가 (숫자·상태·에러코드·산출물 존재 중 하나)
- [ ] 성능 요구에 조건이 붙었는가 (부하·환경·측정 지점 없는 수치는 무의미)
- [ ] 성공 지표에 측정 방법과 기준선이 있는가

### 4. 범위 경계

- [ ] In Scope와 Out of Scope가 충돌하지 않는가
- [ ] 비범위에 "왜 안 하는지"가 있는가
- [ ] 요구사항 중 범위 밖 항목이 섞이지 않았는가
- [ ] "향후 확장" 서술이 요구사항처럼 읽히지 않는가 → 읽히면 MAJOR(범위 무한 확장)

### 5. 일관성 · 추적성

- [ ] `check_traceability.py` ERROR 0건인가 → ERROR는 자동 MAJOR 이상
- [ ] PLAN: 모든 TASK에 근거 REQ가 있고, 실재하는 ID인가
- [ ] PLAN: 모든 MUST REQ가 최소 1개 TASK에 커버되는가 → 미커버 MUST는 CRITICAL
- [ ] 체크리스트: 모든 CHK가 실재 TASK를 참조하는가
- [ ] 절 간 모순(예: 3절 사용자와 7절 요구의 대상이 다름)

### 6. 실행가능성

- [ ] 선행 관계가 성립하는가 (순환 의존 → CRITICAL, 미정의 선행 → MAJOR)
- [ ] 규모 표기가 정책을 따르는가 (S/M/L/XL만)
- [ ] **절대 날짜·임의 인원수가 들어갔는가 → 위반이면 MAJOR** (`estimation-policy.md`)
- [ ] XL 태스크가 분해되지 않고 남아 있는가 → MAJOR
- [ ] 미결 이슈에 의존하는 태스크가 선행으로 표시되었는가

### 7. 리스크 · 가정

- [ ] 가정에 출처가 있는가 (누가/무엇에 근거해 그렇게 전제했는가)
- [ ] 가정이 깨질 때의 영향이 적혔는가
- [ ] 프로젝트를 무너뜨릴 수 있는 리스크가 빠지지 않았는가 (공급/인증/외부 의존/안전)
- [ ] 미결 이슈에 결정 주체가 지정되었는가 → 없으면 MINOR
- [ ] 안전 관련 도메인(모션·전원·의료·차량)인데 안전 요구가 없는가 → CRITICAL

## 라운드 운영

| 라운드 | 기대 |
|--------|------|
| R1 | 구조·완결성 위주. 지적이 많은 것이 정상 |
| R2 | R1 지적 해소 확인 + 남은 명확성/추적성 |
| R3 | 잔여 확인만. **여기서 새 카테고리 지적이 나오면 R1 검수가 부실했던 것** |

- 지적 건수가 직전 라운드보다 늘면 리포트에 `⚠️ 범위 확대 감지`를 적고 새 지적의 정당성을 재검토한다.
- 3라운드 후 잔여가 있으면 잔여를 **문서로 해소 가능 / 사용자 결정 필요**로 분류해 에스컬레이션한다. 임의 통과는 금지.

## 검수 위임이 실패했을 때

검수 에이전트가 리포트를 반환하지 못하는 일이 실제로 발생한다(위임 실패·응답 유실·중단). 이때 지켜야 할 것은 하나다.

> **메인 세션이 대신 검수하지 않는다.** 작성 컨텍스트가 판정까지 겸하는 순간 이 워크플로의 유일한 품질 장치가 사라진다. 검수를 못 한 것은 **결함이 없는 것과 다르다.**

1. **1회 재위임**한다 (동일 프롬프트로 새 호출).
2. 재위임도 실패하면 **검수 미수행 사실을 명시**한다 — 보고에 `검수: 미수행 (위임 실패 2회)`, 문서 `status`는 `draft`로 유지하고 `in-review`로 올리지 않는다.
3. 사용자에게 선택지를 제시한다: `세션 재시작 후 재시도` / `검수 없이 진행(위험 감수 명시)` / `사용자 직접 검수`.
4. 이때 **기계 검증(`check_traceability.py`)은 반드시 실행**한다 — 사람 검수를 대체하지는 못하지만, 추적성·AC·근거 결함은 위임 없이도 잡힌다. 그 결과만으로 "검수 완료"라고 부르지 않는다.

절대 하지 않는 것: 검수 결과를 추정해 채우기 · "지적 없음"으로 간주하기 · 작성 세션이 자체 판정하기.

### 에이전트가 설치되지 않았을 때 (검증된 폴백)

`prd-writer`/`prd-reviewer`가 에이전트 타입으로 잡히지 않으면(설치 직후·세션 재시작 전), 범용 서브에이전트에 **페르소나를 주입**해 역할 분리를 유지한다.

```
범용 서브에이전트 프롬프트 첫 줄:
  "당신은 prd-reviewer 에이전트로 동작합니다.
   먼저 <plugin>/agents/prd-reviewer.md 를 Read하고 그 내용을 당신의 시스템 지침으로
   그대로 채택하십시오 (페르소나·절대 규칙·검수 경계·등급 정의·리포트 형식 포함)."
그 다음 references 절대 경로와 검수 의뢰 본문을 잇는다.
```

메인 세션이 역할을 겸하는 것보다 이 폴백이 낫다 — **다른 컨텍스트에서 파일만 보고 판정**한다는 핵심 성질이 유지되기 때문이다. 폴백을 썼다는 사실은 보고에 남긴다.

### 검수 지적을 메인 세션이 직접 고쳐도 되는 경우

원칙은 "작성은 `prd-writer`"이지만, 지적 한 건 때문에 작성 에이전트를 다시 도는 것이 낭비인 경우가 있다. 기준은 **판단이 필요한가**이다.

| 직접 적용해도 되는 것 | 작성 에이전트로 되돌릴 것 |
|---|---|
| 원문 대조로 참·거짓이 갈리는 오류 — 인용 라인 번호, 오타, 깨진 ID 참조 | 문구 재작성, AC 신설·수정, 요구 강도 변경 |
| 열거 항목 누락처럼 **추가할 내용이 지적문에 그대로 있는** 경우 | 범위·비범위 조정, 미결 이슈 승격 판단 |
| 형식 정정(표 열 정렬, changelog 순서) | 새 REQ 추가, 리스크·가정 변경 |

직접 적용할 때는 **반드시 원문과 대조해 사실을 확인**하고, changelog에 "메인 세션이 직접 적용"을 명시한다. 확인 없이 지적을 그대로 믿고 고치는 것은 검수를 두 번 건너뛰는 것과 같다.
