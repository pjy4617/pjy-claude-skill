# prd-review — 기존 문서 검수 (읽기 전용)

`prd-write`/`prd-plan`의 내부 검수 루프와 **역할이 다르다**.

| | 내부 검수 루프 | **prd-review** |
|---|---|---|
| 대상 | 방금 이 워크플로가 만든 문서 | **외부에서 받은 / 이미 있는** 문서 |
| 결과 | 작성 에이전트가 즉시 수정 | **리포트만** — 수정하지 않는다 |
| 형식 요구 | 이 플러그인 규격 준수 | 규격이 달라도 검수한다(규격 미준수 자체를 지적) |
| 용도 | 산출물 품질 게이트 | 착수 전 판단, 인수인계 검토, 2차 의견 |

## 사용 시기

- 다른 팀·외주·다른 도구가 만든 PRD로 개발을 시작해도 되는지 판단할 때
- 내가 쓴 계획을 **다른 눈으로** 한 번 보고 싶을 때
- 인수인계 받은 문서의 구멍을 먼저 파악할 때
- 이 플러그인이 만든 문서라도 시간이 지나 재검토가 필요할 때

수정까지 원하면: 검수 후 `/prd-write`(PRD) 또는 `/prd-plan`(PLAN)의 반영 루프로 넘긴다.

---

## 실행 절차 (5단계)

### 1단계 — 대상 파악

```bash
wc -l <대상>; head -20 <대상>
```

- 문서 종류 자동 판별: 프론트매터 `id` → 없으면 본문에서 `REQ-`/`TASK-`/`- [ ]` 패턴으로 추정
- 종류가 애매하면 AskUserQuestion으로 확인 (PRD / PLAN / 체크리스트 / 혼합 문서)
- **상위 문서가 있으면 함께 받는다** — 없으면 추적성 판정을 할 수 없으므로 그 한계를 리포트에 명시
- **40KB 초과면** `large-doc-handling.md`의 입력 인제스트 (분할 후 **전 조각** 검수)

### 2단계 — 프로파일 추정

프론트매터에 `profile`이 없으면 내용으로 추정하고 리포트 상단에 `추정 프로파일: hardware-firmware (근거: 전원/커넥터 기술)`처럼 밝힌다. 추정이 틀리면 필수 섹션 판정이 달라지므로 확신이 없으면 사용자에게 확인한다.

### 3단계 — 기계 검증 (가능하면)

```bash
python3 <plugin>/skills/prd-checklist/assets/check_traceability.py --prd <P> [--plan <L>] [--checklist <C>]
```

형식이 이 플러그인 규격과 다르면 스크립트가 `NO_REQ`/`NO_TASK` WARN을 낸다 — 이는 문서의 결함이 아니라 **형식 차이**이므로, 리포트에는 `기계 검증 불가(형식 상이)`로 적고 수동 대조로 대체한다.

### 4단계 — 검수 위임

문서 종류에 맞는 검수자를 Task로 호출한다.

| 대상 | 검수자 |
|------|--------|
| PRD · 혼합 문서 · 규격 밖 외부 문서 | `prd-reviewer` |
| 실행 계획(PLAN) | `prd-plan-reviewer` |
| 체크리스트 | `prd-checklist-reviewer` |

전용 에이전트가 설치되어 있지 않으면 `prd-reviewer`로 대체하고 그 사실을 보고에 남긴다.

```
검수 대상: <경로>  (종류: PRD|PLAN|체크리스트)
상위 문서: <있으면 경로 / 없으면 "없음 — 추적성 판정 제한">
추정 프로파일: <profile>/<stack>
모드: 독립 검수 (수정 없음, 라운드 개념 없음)
references: quality-rubric.md, prd-template-core.md, prd-profiles.md, estimation-policy.md, review-checklist.md
기계 검증 결과: <3단계 출력 또는 "불가(형식 상이)">
```

위임이 실패하면 1회 재위임한다. 그래도 실패하면 **메인 세션이 대신 검수하지 않는다** — 검수 미수행 사실과 기계 검증 결과만 보고하고 재시도 여부를 사용자에게 묻는다 (`quality-rubric.md` → 검수 위임이 실패했을 때).

### 5단계 — 리포트 저장 및 보고

- 리포트 본문을 `docs/reviews/REVIEW-<문서명>-<연번>.md`로 저장 (프로젝트에 `docs/`가 없으면 저장 위치를 사용자에게 확인)
- 요약 보고:

```
검수 완료: <대상> (종류: PRD, 추정 프로파일: software/backend)
판정: 착수 가능 | 보완 필요 | 재작성 권고
집계: CRITICAL n / MAJOR n / MINOR n / INFO n
치명 3건: <한 줄씩>
기계 검증: ERROR n / WARN n | 불가(형식 상이)
리포트: docs/reviews/REVIEW-x-01.md
다음: 보완하려면 /prd-write (PRD) 또는 /prd-plan (PLAN)로 반영 루프
```

- `CRITICAL`이 있으면 AskUserQuestion으로 다음 행동을 묻는다: `보완 루프 시작` / `치명 항목만 수정` / `리포트만 받고 종료`

## 판정 기준

| 판정 | 조건 |
|------|------|
| **착수 가능** | CRITICAL 0 · MAJOR 0 |
| **보완 필요** | CRITICAL 0 · MAJOR ≥1, 또는 CRITICAL이 부분 섹션에 국한 |
| **재작성 권고** | 필수 섹션 다수 부재, 요구사항에 AC가 전무, 범위 경계 없음 — 부분 수정보다 다시 쓰는 게 싼 상태 |

## 하지 않는 것

- 대상 문서 수정 (한 글자도 고치지 않는다 — 그래서 이 스킬은 대상 파일에 Write하지 않는다)
- 승인 판정 (승인은 사용자)
- 문체·취향 지적 (`quality-rubric.md`의 검수 경계 준수)
- 구현 방식 훈수 (필요하면 INFO 등급으로만)
