# 실행 체크리스트 규격

체크리스트는 "할 일 목록"이 아니라 **완료를 증명하는 장부**다. 그래서 항목마다 실행 주체와 **완료 근거** 칸을 강제한다.

## 파일 위치

```
docs/checklist/CHECKLIST-<slug>.md
```

## 프론트매터

```yaml
---
id: CHECKLIST-<slug>
source_plan: PLAN-<slug> (v1.0)
source_prd: PRD-<slug> (v1.2)
status: active | done | superseded
version: 1.0
milestone: M1          # 마일스톤 단위로 파일을 나눈 경우에만
---
```

> **이 문서는 doc-atomize로 분할하지 않는다.** 자주 바뀌고 전수 집계로 읽히므로 원자화의 전제와 맞지 않는다. 커지면 `CHECKLIST-<slug>-M1.md`처럼 **마일스톤 단위로 파일을 나누고** CHK 연번은 파일을 넘어 이어서 부여한다.

## 항목 한 줄 규격 (기계 파싱 대상 — 형식 엄수)

```markdown
- [ ] **CHK-001** (TASK-003) 축 상태 조회 API 스켈레톤 작성 — 주체: agent · 규모: S · 근거:
```

| 요소 | 규칙 |
|------|------|
| `[ ]` | 상태 마크. `` ` ` ``=미착수, `~`=진행중, `x`=완료, `!`=차단 |
| `**CHK-###**` | 3자리 연번. 재사용 금지 |
| `(TASK-###)` | 참조 작업. 여러 개면 `(TASK-003, TASK-004)` |
| 본문 | 무엇을 하면 되는지 한 줄. 완료 여부를 판단할 수 있게 |
| `주체:` | `agent` / `user` / `review` / 역할명(프론트·백엔드·펌웨어) |
| `규모:` | S/M/L (선택 — TASK 규모를 승계) |
| `근거:` | **완료 시 필수.** 파일 경로·테스트 결과·측정값·커밋·리뷰 리포트 경로 |

> **완료 표시(`x`)인데 `근거:`가 비어 있으면 검증 스크립트가 ERROR를 낸다.**
> 이것이 이 체크리스트의 존재 이유다 — "했다고 치는" 완료를 구조적으로 막는다.

### 상태 마크 사용법

| 마크 | 의미 | 근거 칸 |
|------|------|---------|
| `[ ]` | 미착수 | 비움 |
| `[~]` | 진행중 | 진행 상황 메모(선택) |
| `[x]` | 완료 | **필수** — 확인 가능한 증거 |
| `[!]` | 차단 | 차단 사유 + 해소 조건 |

## 문서 구조

```markdown
# 실행 체크리스트 — <프로젝트명>

> 완료 표시는 근거와 함께. 근거 없는 [x]는 검증에서 실패한다.

## M1 — 계약 확정

### TASK-005 — API 계약 확정 (규모 M)
> 근거 요구사항: REQ-020, REQ-021

- [ ] **CHK-001** (TASK-005) 엔드포인트·스키마 초안 작성 — 주체: agent · 근거:
- [ ] **CHK-002** (TASK-005) 프론트/백엔드 합의 확인 — 주체: user · 근거:
- [ ] **CHK-003** (TASK-005) 스키마 검증 테스트 추가 — 주체: agent · 근거:
- [ ] **CHK-004** (TASK-005) AC-020-1 통과 확인 — 주체: review · 근거:

## M2 — 기능 완성
...

## 차단 항목
| CHK | 차단 사유 | 해소 조건 | 관련 OPEN |

## 진척 요약
<!-- prd-checklist --status 로 갱신 -->
```

## 항목 작성 원칙

1. **TASK 하나당 최소 2항목**: 구현과 검증. 한 항목으로 뭉치면 자기검증이 된다
2. **AC를 항목으로 만든다**: PRD의 AC-###-# 마다 확인 항목을 둔다 — 그래야 요구사항이 실제로 검증된다
3. **주체를 섞지 않는다**: `agent`가 할 일과 `user`만 할 수 있는 일(승인·구매·현장 확인)을 한 항목에 넣지 않는다
4. **10분~반나절 단위**: 너무 잘면 관리비가 크고, 너무 굵으면 진척이 안 보인다
5. **검증 항목의 주체는 `review`**: 구현 주체와 다르게 둔다 (레포 원칙: 작성/검증 분리)
6. **차단 항목은 숨기지 않는다**: `[!]`로 표시하고 차단 표에 사유를 남긴다

## 실행 연결

체크리스트는 만들고 끝나는 문서가 아니다.

| 하고 싶은 것 | 방법 |
|--------------|------|
| 이번 세션에서 몇 항목 실행 | 항목을 TodoWrite로 옮겨 진행하고, 끝나면 근거와 함께 `[x]` |
| 독립 항목 병렬 실행 | `parallel-delegation` — 구현/테스트/검증 3-role로 나눠 동시 위임 |
| 여러 세션에 걸친 자동 진행 | OMC `team` / `autopilot`에 체크리스트 경로를 목표로 전달 |
| 진척 집계 | `/prd-checklist --status <경로>` |
| 요구 변경 반영 | `/prd-checklist --sync <경로>` |

## 검증

```bash
python3 <plugin>/skills/prd-checklist/assets/check_traceability.py \
  --prd docs/prd/PRD-x.md --plan docs/plan/PLAN-x.md --checklist docs/checklist/CHECKLIST-x.md
```

| 검출 | 등급 |
|------|------|
| 완료 표시인데 근거 없음 | ERROR |
| 정의되지 않은 AC·OPEN 참조 (`AC_BAD_REF`/`OPEN_BAD_REF`) | ERROR |
| 소속이 다른 번호의 AC 정의 (`AC_PREFIX`) | ERROR |
| 미결 표에만 있고 본문 표기가 없는 OPEN (`OPEN_ORPHAN`) | WARN |
| 존재하지 않는 TASK 참조 | ERROR |
| CHK ID 중복 | ERROR |
| 참조 TASK 없음 | ERROR |
| 실행 주체 표기 없음 | WARN |
| 체크리스트 항목이 없는 TASK | WARN |
