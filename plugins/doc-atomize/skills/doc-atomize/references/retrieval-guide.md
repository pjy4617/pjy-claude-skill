# 조회 가이드 (읽는 쪽)

분할은 절반이다. **조회 규율이 지켜져야** 컨텍스트가 실제로 절약된다.

## 4단계 프로토콜

```
① .claude/atomized/INDEX.md      → 어느 문서인가
② <doc-id>/<doc-id>.index.md     → 라우팅 힌트 · 키워드 역색인 · 목차(↳ 포함 헤딩)로 후보 1~3개
③ parts/<후보>.md 만 Read        → 대개 여기서 끝난다
④ 미스: Grep parts/ → 적중 파일만 Read
   그래도 부족: source_lines 범위로 원본을 offset/limit Read
```

**원본 전체를 Read 하지 않는다.** 원본으로 내려가는 경우는 다음뿐이다:

- 조각 경계를 넘나드는 확인이 필요한데 인접 조각(`prev`/`next`)으로도 부족할 때
- 분할 이후 원본이 바뀐 정황이 있을 때 (인덱스 `generated` vs 파일 mtime)
- 상대경로 자산(이미지 등)의 실제 위치를 확인할 때

## Grep 패턴 예시

```bash
# 특정 문서 안에서 (파일 목록만 — 본문을 컨텍스트에 붓지 않는다)
Grep "TPS62913" --path .claude/atomized/hw-prd/parts --output_mode files_with_matches

# 전 문서 인덱스 일괄 검색 (doc-id 접두 명명 덕분에 가능)
Grep "전원 시퀀싱" --glob "*.index.md"

# 등록된 문서 전체 열거
Glob "**/*.index.md"

# 조각 프론트매터로 좁히기 (특정 장 아래 조각만)
Grep "^path: 5\." --glob "parts/*.md" --output_mode files_with_matches
```

`output_mode: files_with_matches`를 기본으로 쓴다. 적중 본문을 통째로 받으면 조각화의 이득이 사라진다.

## 출처 표기

답변에는 조각 id와 원본 라인을 함께 적는다:

```
근거: hw-prd/005-5-전원-설계 (원본 L292-390)
```

`source_lines`가 있으므로 사용자는 원본에서 즉시 확인할 수 있고, 조각이 정본이라 **원문 그대로 인용**해도 안전하다(요약본이 아니다).

## 비용 감각

`temp/HW_PRD.md` 실측 (884줄 / 41.7 KB):

| 방식 | 읽는 양 | 원본 대비 |
|---|---|---|
| 원본 통째로 Read | 41.7 KB | 100% |
| 인덱스 + 조각 1개 | 7.9 + 3.6 ≈ 11.5 KB | **28%** |
| 인덱스 + 조각 3개 | 7.9 + 10.8 ≈ 18.7 KB | 45% |
| 인덱스만 (위치 확인) | 7.9 KB | 19% |

문서가 클수록 이득이 커진다. 같은 문서를 한 세션에서 여러 번 물으면 인덱스는 이미 컨텍스트에 있으므로 두 번째부터는 조각 값만 든다.

**역으로 300줄 미만 문서는 분할이 손해다** — 인덱스가 원본에 육박한다.

## 진짜 지표는 "조회당 조각 수"

위 표에서 보이듯 조각 1개면 원본의 28%, 3개면 45%다. **비용을 정하는 것은 조각 크기가 아니라 몇 개를 여는가**이고, 그 수는 인덱스의 라우팅 힌트·요약이 얼마나 정확히 조각을 지목하느냐로 결정된다. 조각을 절반 크기로 쪼개도 3개씩 열면 아무것도 아끼지 못한다.

### 측정 (분할 후 5회 조회로 확인한다)

실제 질문 5개를 던지고 **매번 Read한 조각 수를 센다.**

| 평균 | 판정 | 조치 |
|---|---|---|
| 1.5개 이하 | 정상 | 그대로 쓴다 |
| 1.5~2.5개 | 라우팅 부족 | 헤맨 질문을 그대로 `routing_hints`에 추가하고 `reindex` |
| 2.5개 초과 | 요약이 변별력을 잃음 | 열었다가 버린 조각들의 요약을 다시 쓴다 → `audit`로 재확인 |

**헤맨 질문이 곧 라우팅 힌트의 원재료다.** 인덱스를 보고도 조각을 못 골랐다면, 그 질문 문구를 그대로 힌트에 넣는 것이 가장 정확한 큐레이션이다 — 상상해서 만든 질문보다 낫다.

```bash
python3 split_md.py audit "<scope_root>/.claude/atomized/<doc-id>"
```

`힌트당 평균 조각 수`가 이 지표의 사전 추정값이다(목표 1.5 이하).

## CLAUDE.md 마커 블록

`doc-atomize-setup`이 주입하는 규칙(참고용 원문):

```markdown
<!-- doc-atomize:start -->
## 원자 분할 문서 사용 규칙

이 환경에는 대용량 마크다운이 원자 분할로 등록될 수 있다 — 등록 문서 관련 질문을 받으면:

1. `.claude/atomized/INDEX.md` (project) + `~/.claude/atomized/INDEX.md` (global) 확인
2. 해당 문서의 `<doc-id>.index.md`를 진입점으로 라우팅 힌트·키워드 역색인·목차에서 후보 조각 특정
3. `parts/*.md`만 Read — **원본 전체 Read 금지**. 미스 시 `Grep parts/` → 적중 파일만 Read
4. 답변에 출처(조각 id·원본 라인범위) 명시
5. 미등록 대형 .md(300줄 이상)를 반복 참조하게 되면 `/doc-atomize <path>` 등록 제안

조각 본문은 원본 그대로다(요약 아님) — 원문 인용에 그대로 쓸 수 있다.
<!-- doc-atomize:end -->
```

## 안티패턴

| 하지 말 것 | 이유 |
|---|---|
| 인덱스 건너뛰고 `parts/` 전체 Read | 분할한 의미가 없다 |
| 조각 파일 직접 수정 | `verify` 실패. 원본을 고치고 `update` |
| 인덱스 마크다운 직접 수정 | 다음 `reindex`/`update`에 덮인다. metadata.json을 고친다 |
| 확실치 않다고 원본까지 같이 읽기 | 조각 + `prev`/`next`로 먼저 시도 |
| 300줄 문서 분할 | 인덱스 유지비가 이득보다 크다 |
| 요약·힌트를 비워둔 채 조각만 잘게 쪼개기 | 조각을 지목하지 못해 3개씩 열게 된다 — 크기가 아니라 조회당 조각 수가 비용이다 |
| 헤맸는데 힌트를 보강하지 않고 넘어가기 | 같은 질문에서 매번 같은 낭비가 반복된다 |
