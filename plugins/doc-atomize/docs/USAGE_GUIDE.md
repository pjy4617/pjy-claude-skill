# doc-atomize 사용 가이드

대용량 마크다운을 **무손실로** 쪼개고, 인덱스로 찾아 읽는 플러그인.

## 무엇을 해결하는가

큰 `.md`를 참조할 때마다 파일 전체가 컨텍스트에 올라온다. 900줄 PRD면 매 질문마다 40 KB다. 요약본을 만들면 총량은 줄지만 **원문 인용이 불가능**해지고, 디테일을 물을 때마다 원본으로 되돌아가야 한다.

doc-atomize는 요약 대신 **분할**한다:

- 조각을 합치면 원본과 sha256이 일치한다 → 조각 자체가 정본, 원문 그대로 인용 가능
- 인덱스가 "어느 조각인지"를 알려준다 → 매 질문마다 조각 1~3개만 읽는다

## 설치

```
/plugin marketplace add pjy4617/pjy-claude-skill
/plugin install doc-atomize@pjy-skills
/doc-atomize-setup
```

셋업은 `.claude/atomized/` + `INDEX.md` + CLAUDE.md 마커를 만든다. **MCP·에이전트 없음** → 세션 재시작 불필요. `python3`만 있으면 된다.

## 5분 사용법

```bash
/doc-atomize docs/HW_PRD.md          # ① 분할 + 인덱스
/doc-atomize --list                  # ② 등록 확인
# ③ 이후 질문은 그냥 하면 된다 — Claude가 인덱스를 먼저 본다
/doc-atomize --update hw-prd         # ④ 원본이 바뀌면
```

### 실측 예 (884줄 / 41.7 KB PRD)

```
조각        : 13개 (최소 35줄 / 최대 106줄 / 평균 68줄)
인덱스      : hw-prd.index.md (7.9 KB, 원본의 19%)
무손실 검증 : OK — 재조립 sha256 일치, 커버리지 884줄 완전
```

| 방식 | 읽는 양 | 원본 대비 |
|---|---|---|
| 원본 통째로 | 41.7 KB | 100% |
| 인덱스 + 조각 1개 | 11.5 KB | **28%** |
| 인덱스만 (위치 확인) | 7.9 KB | 19% |

## 산출물

```
.claude/atomized/
├── INDEX.md                        ← 마스터 카탈로그
└── hw-prd/
    ├── hw-prd.index.md             ← 검색 진입점
    ├── hw-prd.metadata.json        ← 요약·키워드·라우팅 정본
    └── parts/
        ├── 001-문서-정보-1-시스템-개요.md
        ├── 002-2-M-2-M-Key-에지-커넥터-핀아웃.md
        └── … (013까지)
```

**인덱스 파일명에 doc-id가 붙는 이유**: 문서가 여러 개면 `index.md`가 난립해 구분이 안 되고, `INDEX.md`와는 대소문자 한 글자 차이라 Windows/macOS에서 혼동된다. 접두를 붙이면 `Glob **/*.index.md` 한 번으로 전 문서 인덱스를 열거하고 `Grep --glob "*.index.md"`로 전 문서 역색인을 훑을 수 있다.

## 인덱스는 어떻게 생겼나

```markdown
## 라우팅 힌트
| 이런 질문이면 | 조각 |
| 전원 레일 구성·전류 버짓 | 005 |

## 목차
- **005** 5. 전원 설계 → [`005-5-전원-설계`](parts/005-5-전원-설계.md) `L292-390` — 3.3V 입력에서 5개 레일 파생…
  ↳ 5.1 전원 아키텍처 · 5.2 전류 버짓 · 5.3 DC-DC 컨버터 선정 · …(2개 더, 본문 참조)

## 키워드 역색인
- `TPS62913` → 005
- `DP83848` → 001, 004, 005, 006, 007
```

`↳` 줄이 핵심이다. 작은 절이 병합돼도 목차에서 사라지지 않으므로 "SPI Flash 어디?"에 인덱스만으로 답할 수 있다. 장(章) 수준 헤딩은 표시 예산과 무관하게 항상 노출된다.

## 옵션 튜닝

| 문서 유형 | 권장 옵션 |
|---|---|
| PRD·설계서 | 기본값 |
| API 레퍼런스 | `--min-lines 15 --max-lines 120` |
| 회의록 누적본 | `--base-level 2 --max-lines 400` |
| 표 위주 스펙시트 | `--max-lines 400` + 요약 큐레이션 강화 |
| 파일명 ASCII 강제 환경 | `--slug ascii` |

조각이 80개를 넘으면 경고가 뜬다 — 인덱스가 무거워지니 `--max-lines`를 키운다.

**`--max-lines`를 내릴 때는 `--hard-max`도 같이 내린다.** `max-lines`는 하위 헤딩이 있을 때의 하강 기준, `hard-max`는 하위 헤딩이 없을 때의 문단 폴백 기준이라 서로 다른 경로를 담당한다. `--max-lines 100`만 주면 하위 헤딩 없는 절은 기본 400줄까지 남는다.

**크기 조절은 작은 레버다.** 비용을 정하는 것은 조각 크기가 아니라 **조회당 여는 조각 수**다. 250줄을 100줄로 줄여도 매번 3개씩 열면 아무것도 아끼지 못한다. 크기를 만지기 전에 요약과 라우팅 힌트부터 손본다.

## 큐레이션 감사 — 이 분할이 실제로 아낄지 미리 본다

```
/doc-atomize --audit hw-prd
```

```
큐레이션 감사: hw-prd (조각 13개)
  요약         : 큐레이션 11 / 자동 2
  라우팅 힌트  : 7개, 힌트당 평균 조각 1.14개 (목표 ≤1.5)
  힌트 커버리지: 11/13 조각 (85%)
  판정         : BLOCK 1 / WARN 2
  BLOCK S2  003-3-클럭-아키텍처   요약이 빈 문장이다 ("이 절은 …")
  WARN  R3  전원 관련 전부       조각 5개를 가리킨다 — 좁히지 못하는 힌트다
```

세 수치가 조회당 읽을 조각 수의 예고값이다. `--strict`를 주면 BLOCK이 있을 때 exit 1이라 워크플로 게이트로 쓸 수 있고, 분할 스킬은 이 게이트를 통과해야 카탈로그 등록으로 넘어간다.

무엇이 BLOCK인가 — 요약이 비었거나(S1), "이 절은 ~를 설명한다"류 빈 문장이거나(S2), 제목을 그대로 옮겼거나(S3), 자동 폴백(하위 헤딩 나열·표 헤더) 그대로거나(S4·S5), 라우팅 힌트가 없거나 5개 미만(R1·R2)일 때. 전체 코드표는 `references/index-format.md`에 있다.

고치는 곳은 항상 `<doc-id>.metadata.json`이다 — 인덱스 마크다운을 직접 고치면 다음 `reindex`에 덮인다.

## `--in-place` — repo 문서 자체를 재구성

```
/doc-atomize docs/BIG_SPEC.md --in-place
```

`docs/big-spec/`에 인덱스와 조각을 만들고 원본을 치운다. 파괴적이므로:

1. `git status`가 클린이어야 진행
2. 사용자 확인 필수
3. **무손실 검증 PASS일 때만** 원본 제거 (제거 전 `.original-*.bak` 백업)
4. 원본을 가리키던 링크를 찾아 갱신 제안

## 갱신 흐름

```
/doc-atomize --update hw-prd
  → 추가 0 / 변경 2 / 유지 11 / 삭제 0
  → ⚠️ 요약 재검토 필요: 005-5-전원-설계
```

`curated`로 표시된 요약·키워드·라우팅은 슬러그 기준으로 승계된다. 본문이 바뀐 조각의 요약에는 `summary_stale`이 붙어 인덱스에 ⚠️로 뜬다 — 이걸 보고 요약만 다시 다듬으면 된다.

## FAQ

**Q. manual-digest와 뭐가 다른가?**
manual-digest는 PDF/CHM 같은 외부 매뉴얼을 **요약**해 등록한다(원본의 ~0.3%, 손실 있음). doc-atomize는 손안의 `.md`를 **분할**한다(무손실, 조각이 정본). PDF면 manual-digest, 큰 `.md`면 doc-atomize.

**Q. 조각을 직접 고쳐도 되나?**
안 된다. `verify`가 즉시 실패한다. 원본을 고치고 `--update` 한다.

**Q. 인덱스를 직접 고쳐도 되나?**
다음 `reindex`/`update`에 덮인다. `metadata.json`을 고치고 `reindex` 한다 — 거기가 정본이다.

**Q. 요약이 `(요약 필요)`로 나온다.**
표·체크리스트로만 이뤄진 절이라 자동 추출이 실패한 경우다. 하위 헤딩 목록이 대체 요약으로 들어가며, 최종 문장은 큐레이션 단계에서 직접 쓴다. `--audit`이 이런 조각을 BLOCK으로 짚어준다.

**Q. 분할했는데 별로 안 아껴진다.**
조회당 조각 수를 세어 본다. 평균 2.5개를 넘으면 크기 문제가 아니라 라우팅 문제다 — 헤맸던 질문 문구를 그대로 `routing_hints`에 넣고 `reindex`하면 대개 1개로 떨어진다.

**Q. 작은 문서도 분할하면 좋은가?**
아니다. 300줄 미만은 인덱스 유지비가 이득보다 크다.

**Q. 이미지가 깨진다.**
조각 본문을 그대로 두는 것이 무손실의 조건이라 상대경로를 재작성하지 않는다. 인덱스의 `source_dir` 기준으로 해석하면 된다.

## 한계

- ATX 헤딩(`#`)만 인식 — setext(`===`/`---` 밑줄) 미지원
- 상대경로 자산 미재작성
- 무손실 보증은 정규화(BOM 제거·CRLF→LF) 기준
- 분할은 총량을 줄이지 않는다 — 절약은 조회 단계에서 발생한다

## 명령 요약

| 명령 | 동작 |
|---|---|
| `/doc-atomize-setup` | 환경 1회 초기화 |
| `/doc-atomize <file.md>` | 분할 + 인덱스 생성 |
| `/doc-atomize <file.md> --in-place` | 원본 자리 재구성 |
| `/doc-atomize --update <id>` | 변경분 반영 (큐레이션 승계) |
| `/doc-atomize --verify <id>` | 무손실·구조 재검증 |
| `/doc-atomize --audit <id>` | 큐레이션 감사 (요약·라우팅 힌트 품질, `--strict`로 게이트) |
| `/doc-atomize --list` | 등록 문서 목록 |
| `/doc-atomize --remove <id>` | 제거 |

## 원본이 바뀌면 자동으로 따라간다 (v1.1.0+)

플러그인에 PostToolUse 훅이 포함되어, **등록된 원본을 수정하는 순간 분할본이 갱신**된다.

```
docs/prd/PRD-x.md 수정
  → 변경 1 / 유지 11 / 삭제 0 — 바뀐 조각만 재생성
  → 무손실 재검증 자동 수행
  → ⚠️ 요약 재검토 필요: 009-10-리스크   ← 이것만 사람이 마무리
```

등록되지 않은 문서는 건드리지 않으므로, 분할 전이나 검수 루프 중에는 아무 일도 일어나지 않는다.
훅이 실패해도 편집은 막히지 않는다(항상 exit 0) — 실패 시 `--update` 안내만 돌아온다.
