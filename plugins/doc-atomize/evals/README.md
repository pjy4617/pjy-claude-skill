# doc-atomize eval 스위트

`doc-atomize` 스킬의 **마크다운 원자 분할 흐름** 하나를 검증한다. 케이스 5개 = 발동 3 + 발동금지 2.
`doc-atomize-setup`(환경 1회 초기화)과 PostToolUse 자동 갱신 훅은 이 스위트에 포함되지 않는다.

## 실행

```bash
cd plugins/doc-atomize
claude plugin eval . --ablation with-without --judge-model opus --allow-tools Bash --no-publish
```

파일럿(보정용 1회전)은 `--runs 1` 을 덧붙인다. 읽어야 할 숫자는 합격률이 아니라
**Δ(플러그인 있는 팔 − 없는 팔)** 다. Δ가 0에 가까우면 이 스킬이 없어도 같은 답이 나온다는 뜻이다.

## 실행 전 준비

`socat` 이 있어야 한다. `Bash` 권한을 주면 러너가 실행을 OS 샌드박스에 가두는데 그 백엔드가
`bubblewrap` + `socat` 을 요구한다. 없으면 모든 실행이 몇 초 만에 거부된다.

```bash
sudo apt install socat
```

## 필수 플래그 — `--allow-tools Bash`

스킬 프론트매터의 `allowed-tools` 는 실행 안에서 권한으로 쳐주지 않는다. 운영자가 직접 줘야 한다.
이 플러그인은 `split_md.py` 를 `python3` 로 돌리는 것이 작업의 전부이므로, Bash 가 없으면
발동 케이스 3개가 **양쪽 arm 모두 0점**이 되고 "플러그인이 아무것도 안 했다"로 읽힌다.

`Write` 와 `Edit` 는 일부러 주지 않는다. eval 샌드박스는 `.claude/` 경로에 대해 이 두 도구를 거부하고
Bash 경유 쓰기만 통과한다(manual-digest 스위트에서 실측된 것과 같은 제약). doc-atomize 의 산출물은
전부 `.claude/atomized/` 아래에 생기므로, `Write` 를 허용하면 에이전트가 그 도구를 먼저 골랐다가
막혀서 작업을 포기할 수 있다.

판정 모델은 에이전트 모델과 달라야 한다(자기 편향). 케이스가 `model: sonnet` 이므로 `--judge-model opus`.

### 케이스를 고친 뒤 — 유료 실행 없이 로드만 검증

```bash
cd plugins/doc-atomize
claude plugin eval . --case '*' --runs 1 --max-cost-usd 0 --no-publish --no-scaffold --allow-tools Bash
```

통과 조건 세 가지 — 케이스 5건이 모두 인식될 것(`2 arms × 5 cases`),
`cannot pass with the granted tools` 경고가 0건일 것, 로드 에러가 없을 것.
이 실행이 만든 `evals/results/<timestamp>/` 는 지운다.

## 픽스처를 프롬프트 안에서 만든다

케이스는 매번 빈 샌드박스에서 시작하고 `evals/` 안의 파일은 그리로 복사되지 않는다.
그래서 각 프롬프트가 앞부분에서 **파이썬으로 대상 문서를 직접 만든 뒤** 그것을 분할한다.

발동 케이스 3개가 쓰는 픽스처는 동일하다 — `docs/acme-fx220-hw-spec.md`,
**628줄 / 49.8 KB / 헤딩 34개**의 가상 하드웨어 설계 사양서다. 생성 스크립트는 난수도 시각도
쓰지 않으므로 **바이트 단위로 재현된다**. 그래서 원본 sha256 이 고정값이고, 그 값을 그레이더가
직접 들고 있다(아래 `e-source-hash-recorded`).

```
sha256(docs/acme-fx220-hw-spec.md) = e601fd715292d56657be333569590ce99eb76d3f63797a1aa51c8a22e3a067a5
```

**생성 스크립트를 고치면 이 해시가 바뀐다.** 고쳤으면 01·02 의 `e-source-hash-recorded` 와
03 의 `d-source-hash-updated` 에 든 상수를 함께 갈아야 한다. 안 갈면 두 팔 모두 0점이 되고
그것은 플러그인 회귀가 아니라 스위트 고장이다.

내용은 실존 부품과 실존 보드가 아니다(ACME FX220, XC7A100T 조합, E-0x21~E-0x6A 코드).
모델이 파일을 읽지 않고 기억으로 요약을 지어내면 반드시 틀리게 만들기 위해서다.

## 케이스 구성

| 케이스 | 입력 모양 | 무엇을 보는가 |
|--------|-----------|----------------|
| `01-slash-split` | `/doc-atomize docs/acme-fx220-hw-spec.md` | 산출물 일습(조각·인덱스·metadata·카탈로그), 원본 해시 기록, 조각 본문이 원문 그대로인가, 큐레이션 게이트(라우팅 힌트·요약)가 채워졌는가 |
| `02-nl-context-pain` | 슬래시 없이 "질문마다 통째로 읽게 되니 컨텍스트가 크다. 원문은 하나도 바뀌면 안 된다" | 트리거 민감도 + 같은 산출물 계약. 분할이라는 말을 쓰지 않은 요청에서도 서는가 |
| `03-update-after-edit` | 분할 등록 → 원본에 11장 추가 → "분할본을 원본과 맞는 상태로" | 갱신이 변경분만 반영하는가, 새 절이 조각·인덱스에 들어왔는가, **기존 큐레이션이 승계되는가**, 원본 해시가 갱신됐는가 |
| `04-neg-small-note` | 45줄 회의록 + "조각내서 인덱싱해 두는 게 좋을까요?" | **분할하면 안 됨** — 300줄 미만 정지 규칙. 동시에 회의록 질문에는 제대로 답하는가 |
| `05-neg-code-split` | 488줄 파이썬 파일 + "모듈로 쪼개려면 어떤 경계로?" | **발동하면 안 됨** — "쪼개 달라"·"컨텍스트가 부담"이 그대로 들어간 과발동 미끼. 코드 분할안을 답하는가 |

`04` 와 `05` 는 성격이 다르다. `05` 는 스킬이 **뜨면 안 되는** 케이스(`tool_used: Skill, max: 0, arm: both`)고,
`04` 는 스킬이 떠도 되지만 **분할을 실행하면 안 되는** 케이스다 — 스킬 자신의 정지 규칙("300줄 미만이면
인덱스 유지비가 더 크다")을 지키는지 보는 것이라, 발동 여부가 아니라 산출물 유무로 채점한다.

## 채점 기준

### 발동 케이스 — "분할했다고 했는데 절반만 생긴" 회귀를 겨눈다

| 그레이더 | 타입 | 가중 | 본다 |
|---|---|---|---|
| `a-parts-created` | regex/files | 1 | `.claude/atomized/<id>/parts/*.md` 생성 |
| `b-index-created` | regex/files | 1 | `<id>.index.md` 생성 |
| `c-metadata-created` | regex/files | 1 | `<id>.metadata.json` 생성 |
| `d-catalog-entry` | regex/file | 1 | 마스터 `INDEX.md` 에 항목 등록 |
| `e-source-hash-recorded` | regex/file | 1 | metadata 에 **실제 원본 sha256** 이 적혔는가 |
| `f-line-pointers` | regex/file | 0.5 | 인덱스에 `L###-###` 줄 포인터 3곳 이상 |
| `g-part-body-verbatim` | regex/file | 0.5 | 3장 조각에 원문 토큰(TPS62913·TPS3808·INA226)이 순서대로 남아 있는가 |
| `h-routing-hints` | regex/file | 1 | `routing_hints` 가 비어 있지 않은가 (큐레이션 게이트의 핵심) |
| `i-curated-summary` | regex/file | 0.5 | `summary_source: curated` 가 하나 이상 |
| `j-no-placeholder` | regex/file | 0.5 | 인덱스에 `(요약 필요)` 가 남지 않았는가 |
| `k-summaries-discriminative` | llm | 1 | 인덱스만 보고 조각을 고를 수 있는가 (실질) |
| `l-report-path` | regex/last_message | 0.5 | 마무리 보고에 산출물 경로 명시 |
| `z-skill-fired` | tool_used | 비채점 | 트리거 표시용 |

### 무손실을 따로 채점하지 않는 이유

이 플러그인의 간판 주장은 "재조립하면 원본과 sha256 이 일치한다"다. 그런데 그 판정은
**스킬 안에 이미 게이트로 들어 있다** — `split` 이 무손실 검증을 돌리고, 실패하면 5단계에서 멈춰
조각을 폐기하라고 지시한다. 무손실이 깨지면 스킬은 등록을 완주하지 못하고, 그러면 위 `a`~`d` 가
그대로 떨어진다. 그래서 무손실은 **간접적으로** 채점된다.

대신 두 가지를 직접 본다.

- `e-source-hash-recorded` — metadata 에 적힌 원본 해시가 **우리가 아는 진짜 값**인가.
  다른 파일을 읽었거나 해시를 지어냈으면 여기서 걸린다.
- `g-part-body-verbatim` — 조각 본문이 요약·재작성이 아니라 **원문 그대로**인가.

에이전트에게 "재조립 해시를 파일에 적어라"고 시키는 방식은 쓰지 않았다. 검산을 대상에게
맡기는 꼴이라 원본 해시를 두 번 적어도 통과해 버린다 — 측정이 아니라 자기신고가 된다.

### 경로가 박힌 그레이더의 한계

`e`·`g`·`03-e-new-body-verbatim` 은 `split_md.py` 가 만드는 **정확한 조각 파일명**을 targets 로 쓴다
(`parts/003-3-전원-설계.md`). 슬러그 규칙이나 기본 분할 옵션을 의도적으로 바꾸면 이 그레이더들이
떨어지는데, 그것은 회귀가 아니라 **스위트를 함께 갱신해야 한다는 신호**다.
반대로 이 그레이더들은 경계 탐지·병합 규칙이 조용히 어긋나는 것을 잡아내는 유일한 장치이기도 하다.
가중치를 0.5 로 둔 것은 그 양면성 때문이다.

### 발동금지 케이스는 "아무것도 안 하기"로 만점을 못 받는다

`04`·`05` 모두 **질문에 제대로 답했는지**를 llm 그레이더가 함께 본다. 그것이 없으면
가만히 있는 것이 최적 전략이 되어 버린다. 루브릭은 좁게 썼고, 끝에 **위반이 아닌 것**을 적어 뒀다
(부가 조언, 나중에 커지면 분할하라는 제안, 답변 길이 등) — 판정자가 취향으로 떨어뜨리지 않게 하려는 것이다.

`05` 의 정답은 **Δ 0.00 에 양쪽 1.00** 이다. 여기서 Δ가 생기면 개선이 아니라 과발동이라는 뜻이므로,
Δ를 만들려고 프롬프트나 루브릭을 설계하면 안 된다.

## 이 스위트가 지키는 최소 규칙

1. 발동하면 안 되는 케이스가 최소 1건 남아 있다 (여기서는 `04`·`05` 두 건).
2. 모든 케이스에 결과 채점자가 최소 1개 있다. `tool_used: Skill` 만으로 채점하는 케이스는 없다.
3. 정식 측정은 `runs: 3` 이상으로 돌린다.
4. `--ablation with-without` 로 돌린다.

## 케이스를 늘릴 때

같은 프롬프트의 변형이 아니라 **입력 모양**을 늘린다. 지금 없는 모양은 세 가지다 —
① `--in-place`(원본 자리 재구성, git 클린 게이트와 원본 삭제 순서를 본다),
② PostToolUse 자동 갱신 훅(원본을 Edit 했을 때 훅이 재분할하는가 — 훅은 실행 안에서도 동작한다),
③ 조회 측(분할된 문서에 질문을 던져 **조각 1~3개만 읽고 답하는가** — 이 플러그인이 아끼겠다고
약속한 토큰이 실제로 아껴지는지는 여기서만 측정된다).

③ 이 가장 중요한 빈칸이다. 지금 스위트는 "분할이 제대로 됐는가"까지만 재고,
"그래서 조회가 싸졌는가"는 재지 않는다.

## 실측 기준선 (2026-09-21, Sonnet 에이전트 / Opus 판정, `--runs 1` 파일럿)

| 케이스 | with | without | Δ | 출처 |
|--------|------|---------|---|------|
| `01-slash-split` | 1.00 | 0.00 | +1.00 | with 는 단독 재실행 |
| `02-nl-context-pain` | 1.00 | 0.00 | +1.00 | 파일럿 |
| `03-update-after-edit` | 1.00 | 0.00 | +1.00 | with 는 프롬프트 수정 후 단독 재실행 |
| `04-neg-small-note` | 1.00 | 1.00 | 0.00 | 파일럿 |
| `05-neg-code-split` | 1.00 | 1.00 | 0.00 | 파일럿 |

평균 Δ **+0.60**. 발동금지 2건의 Δ 0.00 은 정답이다.

**이 표는 한 번의 실행에서 나온 것이 아니다.** 파일럿 1회전(5케이스 × 2팔 = 10회, 277초 / $2.83)에서
`01` 은 플레이크로 0.00, `03` 은 프롬프트 문제로 0.25 가 나왔고, 두 케이스의 with 점수는 그 뒤
단독 재실행($0.67 / $0.76)에서 얻었다. without 점수는 파일럿 값 그대로다.
**정식 기준선은 `--runs 3` 전체 실행으로 한 번에 받아 이 표를 갈아야 한다** — 지금 표는
"고친 뒤 통과하는 것을 확인했다"까지이지 3회전 평균이 아니다.

### 1회차만 보고 케이스를 고치면 안 된다 — 실제로 겪은 것

첫 파일럿에서 `01-slash-split` 이 **with 0.00** 으로 나왔다. 6턴 73초 만에 끝났고 산출물이 하나도 없었다.
같은 케이스를 그대로(한 글자도 고치지 않고) 다시 돌리니 **1.00 만점**, 13개 그레이더 전원 통과였다.
즉 케이스 결함이 아니라 **실행 플레이크**다.

`--runs 1` 은 보정용이지 판정용이 아니다. 0점을 보면 먼저 같은 케이스를 단독 재실행해서
재현되는지 확인하고, 재현될 때만 프롬프트·그레이더를 건드린다. 단독 재실행은 이렇게 한다.

```bash
claude plugin eval . --case '01-slash-split' --runs 1 --ablation none \
  --allow-tools Bash --no-publish --no-scaffold --keep-temp
```

`--keep-temp` 를 붙이면 그 실행의 샌드박스(작업 디렉토리 + `out/trace.jsonl`)가 남아
무엇을 하다 멈췄는지 볼 수 있다. 트레이스는 실행이 끝난 뒤에 기록되므로 도중에 열어도 비어 있다.

### `03-update-after-edit` 은 프롬프트를 조였다

파일럿에서 이 케이스만 **with 0.25** 가 나왔다. 뜯어보니 플러그인 쪽 결함이 아니었다 —
1단계(분할·큐레이션)는 성공해서 `summary_source: curated` 와 `routing_hints` 가 멀쩡히 남았는데,
2단계(11장 추가 후 갱신)를 아예 시작하지 않았다. 19턴에서 멈췄으니 턴 부족도 아니다.
한 프롬프트 안의 **두 번째 지시를 흘린 것**이다.

그래서 그레이더는 그대로 두고 프롬프트만 고쳤다 — "이 요청은 둘째 단계까지 끝나야 완료다",
"등록이 끝나면 멈추지 말고 이어서", 그리고 마지막에 보고 요구를 한 줄 더. 채점 기준을 낮춘 것이
아니라 **측정하려던 것(갱신 경로)에 도달하게 만든 것**이다.

이 케이스가 구조적으로 무거운 것은 사실이다. 한 실행 안에서 등록과 갱신을 연달아 시켜야
`--update` 의 큐레이션 승계를 볼 수 있기 때문인데, 그만큼 "두 번째 지시를 흘리는" 실패 모드에
취약하다. 다시 떨어지면 케이스를 둘로 쪼개는 것(등록만 / 이미 등록된 상태에서 갱신만)을 검토한다.

인덱스에 11장 반영, 기존 큐레이션 승계, 원본 해시 갱신, 새 본문 원문 보존, 변경 보고 LLM 판정 PASS×3.
